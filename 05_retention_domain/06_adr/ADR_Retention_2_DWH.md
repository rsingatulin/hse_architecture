## **ADR-RT-02. Customer DWH и разделение OLTP/OLAP**

| Поле | Значение |
| ----- | ----- |
| Версия / дата | 1.0 / 12.11.2026 |
| Статус | Предложено |
| Проблемы | RT-P-08 — аналитика на устаревших данных и риск нагрузки на продуктовые БД; RT-P-09 — отсутствие единой модели и дублирование; RT-P-10 — неконтролируемое качество данных |
| Требования | AA-RET-03, DA-RET-03, DA-RET-04, DA-RET-05, SA-RET-02, BR-RET-03 |
| Участники | Команда retention, владелец BI, CRM, маркетинг, финансы, безопасность |

### **Контекст**

As-Is (контейнерная диаграмма): BI-система читает витрины из БД BI, наполняемой ETL из БД CRM и ERP; единая модель данных отсутствует, дублирование клиентов и задержки остатков. Цели: витрины Near Real-Time, полная история для ML, сохранность исторических данных, защита CRM/ERP от аналитической нагрузки, маскирование ПДн для аналитиков.

### **Рассматриваемые варианты**

| Вариант | Преимущества | Недостатки / причина отказа |
| ----- | ----- | ----- |
| Расширить существующую БД BI новыми витринами | Переиспользование | Смешанная нагрузка, слабое управление качеством, нет разделения слоёв |
| Отдельный слой Customer DWH (PostgreSQL): raw-события → conformed → витрины; маскирующий слой для BI; сохранение ETL только для сверки | Единая модель, изоляция OLTP, база для ML и рекомендаций; **выбран** | Новая БД и миграция истории |
| Big-data стек (озеро, Spark) | Задел на масштаб | Неоправдан для масштаба кейса, бюджет и компетенции (в проде нет K8s, ручные развёртывания) |

### **Выбранное решение**

Слои: **raw** (append-only журнал событий, ретеншен по политике владельцев данных), **conformed** (измерение клиента по подтверждённому customerId, факт продажи, бонусные операции), **витрины** (RFM/сегменты, признаки churn, эффективность кампаний, входы Recommendation Service). Аналитики и BI обращаются **только к витринам**; прямые запросы к CRM/ERP запрещены (AA-RET-03).  
Масштаб и допущения: расчёт по DOC-10 (95 000 постоянных клиентов, 180 онлайн-заказов/сутки, 950 продаж в магазинах/сутки, \+20 % годового роста онлайн). Показатели DOC-17 (1 млн клиентов, 100+ магазинов) противоречат DOC-10 и трактуются как консервативная верхняя граница; ёмкость проверяется нагрузочной проверкой, расхождение документов вынесено в открытые вопросы.  
Качество (DA-RET-04): правила приёма (полнота, уникальность eventId, ссылочная целостность customerId), дашборд качества, карантин бракованных записей; владельцы: маркетинг — клиент/бонусный счёт, финансы — продажи/отчётность. Маскирование (SA-RET-02): витрины хранят псевдонимизированный идентификатор; реальные контакты — только в CRM по ролям; отказ от персонализации инвалидирует персональные наборы.  
История (DA-RET-05): одноразовая загрузка существующей истории из БД CRM/ERP штатным ETL, далее — события; обратная совместимость витрин и возможность анализа трендов за несколько лет сохраняются.

### **Обоснование**

Отделение OLAP защищает CRM/ERP (AA-RET-03), даёт единую модель вместо дублей и служит источником признаков для RT-004 и Recommendation Service без новых тяжёлых платформ в рамках бюджета.

### **Связанные требования**

| Требование | Как поддерживается |
| ----- | ----- |
| AA-RET-03 | Аналитика только по витринам DWH |
| DA-RET-03 | Полная история событий и признаков для ML |
| DA-RET-04 | Правила качества, владельцы, дашборд |
| SA-RET-02 | Псевдонимизация и ролевой доступ |

### **Последствия и риски**

Новое хранилище и его резервирование; effort на миграцию истории; риск расхождения conformed-слоя и CRM — митигируется сверкой.

### **Проверка**

| Проверка | Ожидаемый результат |
| ----- | ----- |
| BI-запрос к CRM/ERP | Заблокирован архитектурно |
| Дубликаты событий | Нет двойного учёта в витрине |
| Возраст витрины | Метрика ≤15 мин в норме |
| Отказ клиента от персонализации | Исключён из персональных витрин и выдачи рекомендаций |
| Миграция истории | Тренды за несколько лет доступны без потерь |
