# Архитектура приложений интернет-продаж RetailMax As-Is

| Поле | Значение |
|---|---|
| Идентификатор | EC-HW-04 / APP-EC-001 |
| Версия | 1.0 |
| Дата | 2026-10-08 |
| Автор | Группа 4, домен интернет-продаж |
| Статус | Черновик As-Is по учебным материалам |
| Основание | Практическая работа, слайд 20 главы 4 |
| Связанные модели | BP-04 As-Is, C4-EC-001/002, UML-EC-001/002, AM-EC-001 |

Модель описывает текущее состояние IS-03 «Интернет-магазин» и процесс BP-04. Интернет-магазин показывает копию каталога и остатков, принимает заказ и оплату, передает заказ в ERP и клиентские данные в CRM. После регистрации заказа ERP передает задание в WMS. Ошибки обмена требуют ручного разбора. Проверка фактической возможности комплектации происходит на складе, поэтому показанное наличие не гарантирует исполнение оплаченного заказа.

Внутренняя программная структура IS-03 в исходных документах не раскрыта. Container и Component представляют минимальную логическую реконструкцию существующих функций. Названия модулей введены для согласованности моделей, а технологии и физическая топология оставлены неизвестными. Модель не устанавливает наличие микросервисов, брокера, API Gateway, автоматических повторов или резервирования до оплаты.

## 2. Границы системы и окружение

**Система в фокусе:** IS-03 «Интернет-магазин». Внутри границы находятся пользовательский интерфейс, прикладная логика и логическое хранилище данных сайта. Существование отдельных развертываемых фронтенда и backend не подтверждено, поэтому интерфейс показан компонентом Web Application.

**Пользователи:** покупатель и оператор интернет-магазина. Покупатель выбирает товар, оформляет, оплачивает и отслеживает заказ. Оператор сопровождает исполнение и разбирает сбои согласно допущениям существующей BPMN.

| Внешний элемент | Роль и связь с интернет-продажами |
|---|---|
| IS-01 ERP | Источник каталога и цен, получатель интернет-заказа. После регистрации передает задание в WMS |
| IS-02 CRM | Хранит клиентские данные и историю заказов/покупок |
| IS-05 WMS | Получает задание от ERP. Склад проверяет фактическое наличие и комплектует заказ с использованием WMS |
| IS-07 Integration Platform | Уже существует. DOC-05 показывает связь с IS-03, но не определяет точные маршруты конкретных операций |
| Система оплаты | Условная внешняя система для детализации шага оплаты. Провайдер и способ подключения не указаны [A-C4-03] |
| Служба доставки | Получает сведения об отгрузке и доставляет товар. Физическую передачу выполняют сотрудники склада и доставки |

C4 Context показывает также цепочку ERP - WMS - доставка, чтобы объяснить окружение BP-04. Эти связи не означают прямой вызов WMS из интернет-магазина. BI и POS не включены: они не участвуют непосредственно в выбранном сценарии оформления. Суточная аналитическая загрузка остается отдельным процессом.

## 3. C4 Container

| Контейнер | Ответственность | Технология и границы достоверности |
|---|---|---|
| Web Application | Каталог, корзина, регистрация/вход, прием оплаты, оформление и просмотр заказа | Серверное веб-приложение. Язык, фреймворк и структура развертывания не указаны |
| Shop Data Store | Копия каталога и остатков, корзины, заказы, регистрационные данные | Логическое хранилище. СУБД, число физических БД и раздельность схем не указаны |

Контейнер C4 означает приложение или хранилище, а не Docker-контейнер. Пара Web Application / Shop Data Store представляет минимальную реконструкцию [A-C4-01]. Для подтвержденной физической модели нужны схема развертывания и обследование IS-03.

| Обмен | Текущий режим по выбранным источникам |
|---|---|
| Web Application - ERP | REST API. Каталог обновляется каждые 15 минут, заказы передаются после оформления и оплаты в сценарии DOC-03 |
| Web Application - CRM | REST API. Данные клиента передаются после регистрации и оформления заказа |
| Web Application - Integration Platform | Связь присутствует в обзорной схеме DOC-05. Конкретные операции не назначаются платформе без подтверждения |
| Web Application - система оплаты | Оплата входит в BP-04. Транспорт и механизм получения результата неизвестны |
| Web Application - Shop Data Store | Логический доступ к данным. Технический протокол неизвестен |

## 4. UML Component

**Выбранный контейнер:** Web Application. Он содержит основную прикладную логику BP-04 и связывает пользовательские действия с оплатой, ERP и CRM. Компоненты находятся внутри одного контейнера и не обозначают отдельно развертываемые сервисы.

| Компонент | Предоставляемый интерфейс | Ответственность | Используемые интерфейсы |
|---|---|---|---|
| Web Interface | IWebUI | Страницы каталога, оформления и сопровождения заказа | ICatalog, ICustomer, IOrder |
| Catalog Module | ICatalog | Чтение копии каталога/остатков и обновление из ERP | IERPExchange, IShopData |
| Customer Module | ICustomer | Регистрация/вход и работа с данными покупателя | IShopData, ICRMExchange |
| Order Module | IOrder | Координация оформления, оплаты и передачи заказа | ICatalog, ICustomer, IPayment, IERPExchange, ICRMExchange, IShopData |
| Payment Adapter | IPayment | Представляет взаимодействие со способом оплаты | Payment Interface, протокол не определен |
| ERP Adapter | IERPExchange | Получение каталога и передача заказа | ERP REST API |
| CRM Adapter | ICRMExchange | Передача клиента и данных заказа/покупки | CRM REST API |
| Shop Repository | IShopData | Чтение и сохранение данных интернет-магазина | Data Access, протокол не определен |

Внутри контейнера строка `provides` обозначает предоставляемый интерфейс, а пунктирная зависимость с именем контракта - его использование. Внешние предоставляемые интерфейсы показаны кругами со сплошной связью к системе, зависимости `uses` - пунктирными стрелками. Имена внутренних интерфейсов и операций условные [A-UML-01]. Они описывают разделение функциональных обязанностей, а не обнаруженные классы или API из исходного кода.

Маршруты IS-07 не раскрываются в Component и Sequence [A-C4-02]. Для конкретных обменов с ERP/CRM выбраны INT-03/04 из DOC-05. Это сохраняет различие между существующей обзорной платформой и документированными прямыми обменами.

## 5. UML Sequence и бизнес-сценарий

**SC-EC-01:** оформление интернет-заказа от выбора товара до регистрации в ERP и получения задания WMS.

**Предусловие:** покупатель работает с сайтом, копия каталога доступна. Авторизация выполняется в процессе, как описано в DOC-03. **Успешный результат:** оплата выполнена, ERP зарегистрировала заказ, WMS получила задание на комплектацию. Получение задания еще не доказывает наличие товара и успешную доставку.

1. Web Interface запрашивает Catalog Module. Через Shop Repository модуль получает товар и наличие из копии сайта. Обновление из ERP раз в 15 минут существует отдельно от оформления каждого заказа.
2. Покупатель оформляет заказ, регистрируется или входит. Customer Module получает идентификатор покупателя, Order Module сохраняет оформляемый заказ [A-UML-01].
3. Payment Adapter представляет выполнение оплаты. Способ оплаты и получение подтверждения абстрагированы [A-C4-03]. При неуспешной оплате текущая попытка заканчивается по BPMN A4.
4. CRM Adapter передает клиента и заказ. Ошибки направляются оператору. Независимость обмена с CRM от исполнения наследует допущение BPMN A3.
5. ERP Adapter передает оплаченный заказ. ERP регистрирует его. При сбое оператор разбирает результат и при возможности вручную повторяет сбойный шаг.
6. ERP передает задание в WMS. При сбое передачи оператор разбирает ситуацию и при возможности повторяет этот шаг. Если восстановление невозможно, заказ остается на ручном урегулировании.

На диаграмме используются `alt`, `opt` и `break`. Сплошные стрелки абстрагируют вызов или действие, пунктирные - результат. Наличие REST в DOC-05 не доказывает устройство внутренних вызовов и callbacks. Асинхронные сообщения, брокер и автоматические повторы в модель не добавлены.

Ручная сверка наличия заказа/задания перед повтором введена как уточнение ручного разбора [A-UML-02]. Это не подтверждение существующей автоматической защиты от дублей. При неизвестном результате передачи нельзя считать, что получатель ничего не записал.

Комплектация, доставка и передача истории покупки в CRM продолжают BP-04 за границами SC-EC-01. Расхождение фактического наличия выявляется на складе согласно BPMN A1. Такая граница позволяет подробно показать оформление, не превращая Sequence в диаграмму всего логистического процесса.

## 7. Проблемы As-Is и связь с требованиями

Требования REQ-EC описывают желаемый результат проекта. Их связь с As-Is показывает причины изменений, а не подтверждает выполнение целевых показателей.

| Проблема | Где видна в модели As-Is | Связанное требование |
|---|---|---|
| EC-P-01: неактуальные остатки | Catalog Module использует копию с обновлением раз в 15 минут. Фактическая проверка происходит позже на складе | REQ-EC-001 |
| EC-P-02: длительная обработка | Оплата, регистрация в ERP и передача задания разделены. Сбои возвращают процесс на ручной разбор | REQ-EC-002/003 |
| EC-P-03: пиковая нагрузка | Каталог и оформление находятся в общей границе Web Application. Возможность независимого масштабирования не установлена | REQ-EC-004/005 |
| EC-P-04: точечные интеграции | ERP Adapter и CRM Adapter связаны с API систем. Роль IS-07 в конкретных маршрутах не уточнена | REQ-EC-006 |
| EC-P-05: дубли клиентов | Customer Module передает клиента в CRM. Единый механизм дедупликации не подтвержден | REQ-EC-009 и управление данными DOC-17 |
| EC-P-06: ручные ошибки обмена | Оператор разбирает ошибки передачи заказа и задания, повтор выполняется вручную | REQ-EC-007 |
| EC-P-08: медленные релизы | Все логические функции показаны внутри выбранного приложения. Реальное разделение сборок и развертываний требует обследования | REQ-EC-008 |

Срок «не более 10 минут» из REQ-EC-003 и «не более 5 секунд» из DOC-17 не используются как текущие задержки. Это целевые требования с разными или неуточненными границами измерения. В Sequence нет выдуманных таймеров.

## 8. Допущения и противоречия источников

| ID | Допущение или ограничение | Основание и необходимая проверка |
|---|---|---|
| A-C4-01 | Web Application и Shop Data Store - минимальная логическая реконструкция. Единое физическое приложение/БД не доказаны | DOC-04 перечисляет функции и данные, но не описывает deployment. Нужны схема развертывания, стек и состав хранилищ |
| A-C4-02 | Для конкретных ERP/CRM-обменов выбрана детализация DOC-05. Связь IS-03 - IS-07 оставлена обзорной | DOC-05 содержит прямые INT-03/04 и платформу в обзорной схеме. DOC-16 также описывает файловые каналы и WMS - сайт. Нужно подтвердить маршруты и режимы, номер документа не доказывает его актуальность |
| A-C4-03 | Прием оплаты раскрыт через условную внешнюю систему и Payment Adapter | DOC-03/04 задают оплату, но не провайдера и интерфейсы. Нужно подтвердить платежную интеграцию и сценарии оплаты |
| A-UML-01 | Внутренние модули, интерфейсы, идентификатор заказа и операции хранения - функциональная реконструкция | Нет исходного кода IS-03. Не утверждаются конкретные классы, транзакции и API |
| A-UML-02 | Ручной разбор может включать сверку результата перед условным повтором | Детализация BPMN A2. Нужно подтвердить полномочия оператора, способ сверки и порядок предотвращения дублей |
| BPMN A1 | Фактическое наличие уточняют при комплектации | Сохраняется допущение существующей BPMN; точное место выявления требует согласования |
| BPMN A2 | Обнаруженный сбой передают на ручной разбор и при возможности вручную повторяют | Не означает наличие автоматических повторов, единого мониторинга или идемпотентности |
| BPMN A3 | Ошибка CRM не блокирует дальнейшее исполнение | Сохраняется как допущение BPMN. Если реальная интеграция блокирующая, ветвь CRM необходимо изменить |
| BPMN A4 | Передача заказа на исполнение происходит после успешной оплаты | Последовательность DOC-03. Повтор оплаты и оплата при получении не детализированы |

## 9. Краткое объяснение для защиты

«В Context мы определили границу интернет-магазина и его окружение. В Container выделили существующее приложение сайта и логическое хранилище, не назначая неизвестные технологии. Для Web Application построили Component: разделили каталог, клиента, заказ и адаптеры интеграций. В Sequence показали оформление по BP-04: наличие из копии, регистрация, оплата, CRM, ERP и задание в WMS. Главный риск As-Is - отсутствие гарантии фактического наличия на этапе оплаты и ручное восстановление обменов. Внутренние модули - логическая реконструкция, которую надо подтвердить обследованием».
