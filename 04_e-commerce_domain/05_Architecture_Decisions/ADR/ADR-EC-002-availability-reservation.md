# ADR-EC-002. Доступность товара и резервирование до оплаты

| Поле | Значение |
|---|---|
| Версия / дата | 1.0 / 22.10.2026 |
| Статус | Предложено |
| Проблемы | EC-P-01, EC-P-02 |
| Требования | REQ-EC-001/002/003/006/007 |
| Участники согласования | E-commerce, Warehouse, владелец ERP, коммерческий отдел, финансы, офлайн-продажи |

## Контекст

Сайт показывает копию каталога и остатков. По DOC-05 она обновляется раз в 15 минут, а BP-04 предусматривает оплату до регистрации в ERP и складской проверки. Копия не защищает последнюю единицу от одновременной продажи. Частое обновление само по себе не устраняет гонку.

DOC-06 назначает WMS источником остатка. [ADR-WH-001](../../../03_warehouse_domain/05_Architecture_Decisions/ADR/ADR-WH-001-inventory-authority.md) предлагает атомарный резерв в WMS и общий orderId. Это совместимое предложение, а не подтверждение готового API.

## Рассматриваемые варианты

| Вариант | Преимущества | Недостатки / причина отказа |
|---|---|---|
| Учащать загрузку остатков и оплачивать по копии | Небольшое изменение сайта | Между чтением и оплатой товар всё равно может закончиться |
| Все просмотры выполнять синхронно в WMS | Свежий ответ на момент чтения | Нагрузка на WMS, зависимость каталога от склада; чтение не является резервом |
| Проекция для просмотра + атомарный резерв WMS при оформлении | Быстрый каталог и контролируемая продажа доступного остатка | Оформление зависит от резерва и его срока; **выбран** |
| Самостоятельный учёт и резерв в БД магазина | Автономность онлайн-канала | Второй источник остатка при сохранении WMS, риск двойной продажи |

## Выбранное решение

Каталог и доступность для просмотра хранить в проекции интернет-магазина. Товар/базовая цена поступают из ERP, остаток — из WMS через общий слой. Проекция хранит источник, версию и время актуальности; события применяются по версии, периодическая сверка исправляет пропуски. Порог устаревания согласуется с логистикой. При его превышении сайт не обещает подтверждённое наличие.

Перед оплатой сервис заказа подтверждает цену и состав корзины через общий слой, сохраняет снимок цены/версии и запрашивает резерв WMS. Изменённую сумму покупатель подтверждает до платежа. Правило фиксации цены на срок оформления согласуется с ERP и коммерческим отделом; при неподтверждённой цене списание не запускается.

| Этап | Правило |
|---|---|
| Создание резерва | Один orderId и версия состава; все строки центрального склада резервируются атомарно, частичный заказ в базовом сценарии не принимается |
| Успешный ответ | Сохранить reservationId, версию, статус и expiresAt; затем разрешить начало оплаты |
| Таймаут ответа | Результат неизвестен: повторить тот же идемпотентный запрос/сверить состояние, не создавать новый резерв с новым ключом |
| Нет товара или WMS недоступна | Не начинать оплату; показать отказ/ожидание подтверждения, сохранив корзину |
| Оплата не завершена | По согласованному правилу продлить или освободить резерв; сайт не продлевает его произвольно |
| Оплаченный заказ → ERP → WMS | Передать прежние orderId и reservationId. Задание использует существующий резерв, не резервирует товар повторно |
| Начат подбор | По модели Warehouse резерв становится ALLOCATED и автоматически не истекает; отмена выполняется через задание |

При истечении резерва во время оплаты действует [ADR-EC-003](ADR-EC-003-order-lifecycle.md): подтверждённый платёж не превращает просроченный резерв в действующий. Для оплаченного заказа, ожидающего ERP, нужен поддерживаемый WMS-переход удержания/продления или согласованное окно до передачи в подбор. До выбора этого механизма нельзя обещать наличие только на основании раннего резерва.

Онлайн не списывает остаток по каждому событию заказа/отгрузки: проекцию количества обновляет авторитетное изменение Stock из WMS. Процесс заказа использует события резерва и задания для своих статусов.

## Обоснование

Разделение чтения и резервирования сохраняет быстрый просмотр и переносит решение о последней единице к владельцу остатка. Ранний резерв устраняет архитектурную причину оплаты по неподтверждённому наличию, не создавая второго учёта склада. Решение согласуется с предложением Warehouse и сохраняет ERP в роли учётной системы.

| Требование | Как поддерживается |
|---|---|
| REQ-EC-001 | Версионируемая проекция WMS и подтверждение атомарного резерва |

## Последствия и риски

Уменьшается риск оплаты отсутствующего товара; просмотр не нагружает WMS каждым обращением. Появляются сроки резерва, гонки с платежом, требования к конкурентному API и ограничению злоупотреблений резервами. Резерв не устраняет физическую недостачу или брак — для них остаются исключения исполнения и компенсации.

Политика центрального склада не определяет автономную продажу магазина. Самовывоз и запасы магазинов согласуются с командой 1 отдельно, включая владельца резерва и правила работы без связи.

## Проверка и условия пересмотра

| Проверка | Ожидаемый результат |
|---|---|
| Два заказа на последнюю единицу | WMS подтверждает не более одного резерва; второй заказ не переходит к оплате |
| Утерян ответ резервирования | Повтор возвращает тот же результат, доступное количество не уменьшается повторно |
| Старое событие остатка приходит после нового | Версия проекции не откатывается; разрыв выявляется сверкой |
| Цена изменилась при оформлении | Покупатель подтверждает актуальную сумму; нет списания другой суммы |
| ERP передаёт задание по раннему резерву | Нет второго резерва, один набор исполнения на версию заказа |
| Резерв истёк, платёж пришёл поздно | Нет ложного подтверждения исполнения; выполняется согласованное урегулирование |

Условия утверждения: подтверждены транзакционные возможности WMS и API общего слоя, сроки удержания/продления, политика цены, лимиты резервов и стык с ERP. При невозможности WMS гарантировать резерв требуется совместный пересмотр владельца запасов; кэш не заменяет эту гарантию.
