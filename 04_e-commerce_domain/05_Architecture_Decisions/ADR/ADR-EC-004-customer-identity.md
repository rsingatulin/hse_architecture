# ADR-EC-004. Профиль клиента в CRM без общего MDM

| Поле | Значение |
|---|---|
| Версия / дата | 1.2 / 22.10.2026 |
| Статус | Предложено; отказ от Customer Data Hub и общего MDM задан решением команды |
| Проблемы | EC-P-05 |
| Требования | REQ-EC-009; DA-01/02 из DOC-12, раздел 10 DOC-17; DA-RET-01, AA-RET-04 |
| Участники согласования | E-commerce, команда 5 / CRM, маркетинг, владелец идентификации, безопасность |

## Контекст

В As-Is интернет-магазин передаёт данные клиента в CRM, но единый идентификатор и защита от дублей не подтверждены. DOC-06 определяет CRM источником клиента и бонусного счёта. Учётная запись сайта не делает его вторым владельцем корпоративного профиля.

По решению команды от 22.10.2026 **Customer Data Hub и общий MDM не создаются**. Прежний вариант с обязательным Hub отклонён. Используются CRM и общий интеграционный слой, без нового посредника управления мастер-данными и без переноса его функций в отдельный сервис платформы.

[Требование Retention AA-RET-02](../../../05_retention_domain/01_business_context/Архитектурные_требования.md) пока требует Hub/MDM и подлежит пересмотру с командой 5. Этот ADR намеренно не заявляет соответствия прежнему требованию. Сохраняются CRM как мастер D-02/D-08 и общая платформа как маршрут обмена.

## Рассматриваемые варианты

| Вариант | Преимущества | Недостатки / причина отказа |
|---|---|---|
| Независимые мастер-профили сайта и CRM | Автономность канала | Дублирование и конфликт владельцев данных |
| Общий Customer Data Hub / MDM перед CRM | Единое управление мастер-данными | Новый компонент и отдельный объём внедрения; отклонён решением команды |
| CRM как единственный мастер, обмен через общий слой | Повторное использование существующей системы, один владелец профиля | Требует поддерживаемого CRM-контракта и правил разбора дублей; **выбран** |

## Выбранное решение

Маршрут профиля: **интернет-магазин → общий интеграционный слой → поддерживаемый API/адаптер CRM → CRM**. Общий слой отвечает за доставку, преобразование форматов, контроль доступа и наблюдаемость по [ADR-EC-001](ADR-EC-001-shared-integration.md). Он не ведёт золотую запись клиента и не становится MDM под другим названием.

| Объект / действие | Ответственность |
|---|---|
| Клиентский профиль и customerId | CRM создаёт/находит авторитетную запись и возвращает её стабильный ID |
| Учётная запись и вход | Механизм идентификации; subject учётной записи отличается от customerId |
| Связь channelAccountId / subject ↔ customerId | CRM принимает уникальный внешний ключ канала; сайт хранит подтверждённую связь, а не независимый мастер-профиль |
| Изменение контактов | Поддерживаемая команда CRM с правами пользователя и контролем версии |
| Данные заказа | Подтверждённый customerId и необходимый снимок контактов для исполнения; изменение профиля не переписывает историю заказа |
| Бонусный счёт | CRM — мастер; сервис лояльности команды 5 применяет бонусные правила через общий слой |
| Исторические дубли | Владелец CRM разбирает их штатными средствами и утверждённой процедурой; общая MDM-платформа не проектируется |

### Запись и защита от дублей

Создание/поиск профиля использует channelId, channelAccountId/subject, разрешённые проверенные атрибуты и ключ идемпотентности. CRM сохраняет внешний ключ и результат операции; повтор того же запроса не создаёт вторую карточку. После таймаута проверяется прежняя операция. Подтверждение очереди интеграционного слоя не означает успешную запись CRM.

Если у покупателя уже есть подтверждённый customerId, канал обновляет разрешённые поля этой записи, а не создаёт нового клиента. При изменении контакта ID сохраняется. Для нового канала сопоставление с существующей карточкой выполняется поддерживаемыми правилами CRM; одного общего телефона/email недостаточно для автоматического объединения и доступа к чужой истории.

Автоматическая дедупликация личности между всеми каналами не обещается. Повторы одной операции и исторические карточки одного человека — разные задачи. Неоднозначные совпадения передаются владельцу CRM. При подтверждённом слиянии CRM сохраняет соответствие прежних ID или предоставляет контролируемое обновление ссылок; каналы и аналитика получают результат через общий слой, без потери и удвоения истории покупок.

Если CRM не поддерживает уникальный внешний ключ, идемпотентную запись или проверку неизвестного результата, одного адаптера недостаточно для гарантии отсутствия дублей. Требуется поддерживаемое расширение CRM либо контролируемый разбор неопределённого результата; общий MDM не добавляется автоматически.

### Недоступность и бонусные операции

При недоступной CRM ранее оформленный заказ продолжает исполнение по сохранённым данным. Известная учётная запись использует подтверждённую связь customerId и действующую проверяемую сессию. Новые изменения профиля остаются ожидающими до подтверждения CRM.

Для новой регистрации без подтверждённого customerId запрос сохраняется как PROFILE_LINK_PENDING; подтверждение нового заказа и оплата ждут результата CRM. Новый мастер-профиль локально не создаётся. Это сохраняет правило регистрации/входа BP-04; гостевой checkout не вводится этим ADR.

Бонусные бизнес-команды идут через общий слой к сервису лояльности/поддерживаемому интерфейсу CRM. Универсальная команда обновления профиля не позволяет произвольно менять баланс. Списание подтверждается авторитетной бонусной операцией, а не локальной копией баланса или подтверждением доставки сообщения. Правила автономного списания POS согласуются отдельно.

### Защита данных

Проверять принадлежность профиля пользователю, ограничивать поля и роли, защищать каналы и аудировать критичные действия. Знание customerId не даёт доступа к профилю. Полные контакты и платёжные реквизиты не включаются в технические логи и общие события. Сроки хранения, удаление/обезличивание и разрешённость персонализации определяются владельцами данных и безопасности.

## Обоснование

CRM уже определена источником клиента и бонусного счёта. Использование её API через общую платформу сохраняет один мастер и не требует создания отдельного Hub/MDM. Уникальный внешний ключ и идемпотентность защищают от дублей повторной отправки; проверка и объединение исторических карточек остаются ответственностью CRM и владельца данных.

| Требование | Как поддерживается |

## Последствия и риски

Уменьшается состав компонентов и зависимостей. Надёжность регистрации и предотвращение дублей зависят от возможностей CRM. Отказ от MDM не устраняет исторические дубли автоматически и не гарантирует единую личность по всем каналам без правил CRM. Новый клиент зависит от доступности CRM, ранее оформленный заказ — от сохранённого процесса исполнения.

## Проверка и условия пересмотра

| Проверка | Ожидаемый результат |
|---|---|
| Повтор регистрации с тем же внешним ключом | Та же карточка CRM и тот же customerId |
| Одновременные запросы из разных каналов | Применены правила CRM; неоднозначность не превращается в ошибочное автоматическое слияние |
| Ответ потерян после записи CRM | Проверка/повтор прежней операции не создаёт вторую карточку |
| Смена контакта или запрос чужого customerId | ID сохраняется; права и подтверждение изменения проверены |
| CRM недоступна при новой регистрации | PROFILE_LINK_PENDING, оплаты ещё нет, локального мастер-профиля нет |
| CRM недоступна после оформления заказа | Исполнение продолжается по сохранённым данным; изменение профиля ожидает подтверждения |
| Подтверждённое объединение исторических дублей | Ссылки и история контролируемо обновляются, покупки не удваиваются |
| Обмен бонусами | Поддерживаемая операция сервиса лояльности/CRM, без произвольного изменения баланса в запросе профиля |

До реализации согласовать с командой 5 API CRM, уникальность внешних ключей, права, версии, правила сопоставления и обработку неопределённого результата. Требование AA-RET-02 и модели Retention с Hub/MDM должны быть приведены к новому решению; изменения документов команды 5 этим пакетом не утверждаются.
