# ADR-EC-001. Общий интеграционный слой для интернет-продаж

| Поле | Значение |
|---|---|
| Версия / дата | 1.0 / 22.10.2026 |
| Статус | Предложено; наличие общего слоя задано договорённостью команд, детали требуют согласования |
| Проблемы | EC-P-04, EC-P-06 |
| Требования | REQ-EC-006/007/008/009; AA-01, API First и слабая связанность |
| Участники согласования | Все доменные команды, владельцы ERP/WMS/CRM, ИТ-директор и эксплуатация |

## Контекст

В [As-Is](../../02_Application_Architecture/APP-EC-001-as-is.md) интернет-магазин передаёт заказы и клиентов через отдельные адаптеры, а точные маршруты существующей IS-07 не установлены. DOC-05 и DOC-16 расходятся в описании наличия платформы. Это не меняет целевую договорённость: все команды строят общий интеграционный слой, включая взаимодействие с ERP и WMS.

Нужно определить, как домен использует слой, не дублируя его и не перенося туда все бизнес-правила.

## Рассматриваемые варианты

| Вариант | Преимущества | Недостатки / причина отказа |
|---|---|---|
| Общий слой только как синхронный прокси | Единая точка доступа, небольшой первоначальный объём | Сохраняется длинная цепочка ожидания; нет восстановимой доставки событий |
| Общий слой с API, событиями и адаптерами систем | Немедленные ответы там, где нужны, независимые подписчики, единые контракты | Нужны устойчивое хранение сообщений и эксплуатация; **выбран** |
| Общая ESB с логикой оформления, оплаты и склада | Процесс виден в одном месте | Изменения домена требуют релиза общего компонента; размывается ответственность |

Отдельная интеграционная платформа e-commerce и новые прямые межсистемные связи исключены общей договорённостью команд.

## Выбранное решение

Использовать общий слой для межсервисных и межсистемных обменов: управляемые API для команд/запросов, событийный транспорт для зафиксированных фактов, адаптеры к поддерживаемым интерфейсам ERP/WMS/CRM. Внутренний вызов модуля внутри одного приложения и его доступ к собственному хранилищу не являются интеграцией между сервисами.

| Ответственность общего слоя | Ответственность домена / системы |
|---|---|
| Маршрутизация, аутентификация сервисов, контроль доступа, лимиты | Авторизация конкретного бизнес-действия и допустимые переходы состояния |
| Каталог и версии контрактов, преобразование форматов | Значение полей, источник данных, правила совместимости |
| Доставка, технические повторы, трассировка, карантин | Идемпотентное применение команды, бизнес-повтор и компенсация |
| Адаптация поддерживаемых API систем | Остаток и резерв — WMS; учётный заказ — ERP; профиль — CRM |

Общий слой не становится владельцем заказов или запасов. Логика оформления находится в сервисе заказа по [ADR-EC-003](ADR-EC-003-order-lifecycle.md). API Gateway не заменяет устойчивую очередь и журнал процесса. Проверка прав в получателе сохраняется после проверки на шлюзе.

| Логический обмен через общий слой | Режим | Владелец результата |
|---|---|---|
| Интернет-магазин → ERP: проверка цены | Запрос с ограниченным ожиданием | ERP / согласованный сервис цен |
| Интернет-магазин → WMS: резерв, проверка результата, освобождение | Команда с идемпотентным ключом и бизнес-подтверждением | WMS |
| Интернет-магазин → ERP: регистрация оплаченного заказа | Сохраняемая команда, отдельное подтверждение регистрации | ERP |
| ERP → WMS: задание с существующим резервом | Сохраняемая команда; единственный инициатор задания — ERP | ERP и WMS |
| ERP/WMS/доставка → интернет-магазин: статусы | Зафиксированные события либо адаптированный восстановимый обмен | Система, выполнившая переход |
| Интернет-магазин → Customer Data Hub → CRM / Loyalty | Запросы/команды D-02/D-08; каждый переход через общий слой; Hub обязателен | CRM — мастер, Hub — идентичность, Loyalty — бизнес-операции |
| Источники → BI/рекомендации, история покупки → CRM | События по согласованному контракту, отдельно от записи профиля | Соответствующий владелец данных |

Новые отдельно развёрнутые сервисы e-commerce также используют общий слой для обмена. Внешняя оплата и доставка подключаются через согласованные адаптеры слоя; интерактивная платёжная страница провайдера остаётся пользовательским интерфейсом, а подтверждения серверу проходят контролируемую интеграцию.

Сначала проверить возможности существующей IS-07. Продукт Gateway, брокер и топология выбираются совместно по требованиям, стоимости и компетенциям. Этот ADR не выбирает Kafka, RabbitMQ или отдельный Kubernetes-кластер.

## Обоснование

Сочетание API и событий позволяет подтвердить резерв в момент оформления и доставлять остальные факты независимо от доступности подписчиков. Общий слой повторно используется всеми командами, а доменные правила остаются у владельцев. Это соответствует API First, слабой связанности и ограничению бюджета без дублирования платформ.

## Связанные требования

| Требование | Как поддерживается |
|---|---|
| REQ-EC-006 | Общий маршрут, каталог, версии и владельцы контрактов |
| REQ-EC-007 | Сохраняемая доставка и контролируемая обработка ошибок совместно с ADR-EC-004 |
| REQ-EC-008 | Независимые доменные контракты вместо изменения каждой отдельной связи |
| REQ-EC-009 | Защищённые каналы, сервисные полномочия и аудит |

## Последствия и риски

Сокращаются отдельные связи, контракты становятся общими. Цена решения — общая зависимость, стоимость эксплуатации и необходимость согласования версий. Для слоя нужны резервирование, рассчитанные лимиты/буферы, изоляция потоков, мониторинг очередей и план восстановления. Отказ аналитического подписчика не должен блокировать резервирование. SLA сайта не получается автоматически из наличия шлюза.

## Проверка и условия пересмотра

| Проверка | Ожидаемый результат |
|---|---|
| Новая интеграция ERP/WMS/CRM | Есть владелец, версия, схема, права, ошибки и маршрут общего слоя; прямой обход отсутствует |
| Недоступны Hub/CRM или BI | Ранее оформленный заказ продолжает исполнение; новая регистрация ждёт подтверждения Hub до оплаты; сообщения сохраняются |
| Отказ экземпляра слоя или перегрузка подписчика | Работает согласованный механизм переключения/буферизации; измеряются потери и задержка |
| Несовместимая версия контракта | Блокируется до выпуска; старый потребитель поддерживается в переходном окне |

Пересмотр нужен, если общий слой не обеспечивает поддерживаемую WMS-команду, восстановимость доставки, безопасность или согласованную нагрузку. Изменение проводится совместно; скрытый прямой обход не является запасным решением.
