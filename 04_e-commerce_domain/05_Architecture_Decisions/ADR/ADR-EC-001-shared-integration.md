# ADR-EC-001. Общий интеграционный слой для интернет-продаж

| Поле | Значение |
|---|---|
| Версия / дата | 1.3 / 22.10.2026 |
| Статус | Предложено; наличие общего слоя задано договорённостью команд, детали требуют согласования |
| Проблемы | EC-P-02, EC-P-04, EC-P-06; EC-P-07 в части доставки данных |
| Требования | REQ-EC-002/003/006/007/008/009; AA-01, API First и слабая связанность |
| Участники согласования | Все доменные команды, владельцы ERP/WMS/CRM, ИТ-директор и эксплуатация |
| Заменяет | ADR-EC-003 и ADR-EC-004; их интеграционные решения объединены в этом ADR |

## Контекст

В [As-Is](../../02_Application_Architecture/APP-EC-001-as-is.md) интернет-магазин передаёт заказы и клиентов через отдельные адаптеры, а точные маршруты существующей IS-07 не установлены. DOC-05 и DOC-16 расходятся в описании наличия платформы. Это не меняет целевую договорённость: все команды строят общий интеграционный слой, включая взаимодействие с ERP и WMS.

Нужно определить общий маршрут, координацию обменов заказа и восстановление после ошибок. Эти вопросы объединены в одном ADR; отдельный оркестратор или собственная инфраструктура надёжной доставки e-commerce не предписываются. Бизнес-правила заказа, оплаты, отмен и возвратов будут разработаны отдельно в описании процесса и контрактах владельцев.

## Рассматриваемые варианты

| Вариант | Преимущества | Недостатки / причина отказа |
|---|---|---|
| Общий слой только как синхронный прокси | Единая точка доступа, небольшой первоначальный объём | Сохраняется длинная цепочка ожидания; нет восстановимой доставки событий |
| Общий слой с API, событиями и адаптерами систем | Немедленные ответы там, где нужны, независимые подписчики, единые контракты | Нужны устойчивое хранение сообщений и эксплуатация; **выбран** |
| Вся цепочка заказа в одном синхронном запросе | Простая последовательность при доступных системах | Длинное ожидание и неизвестный результат при разрыве связи; не подходит для восстановления |

Отдельная интеграционная платформа e-commerce и новые прямые межсистемные связи исключены общей договорённостью команд.

## Выбранное решение

Использовать общий слой для межсервисных и межсистемных обменов: управляемые API для команд/запросов, событийный транспорт для зафиксированных фактов, адаптеры к поддерживаемым интерфейсам ERP/WMS/CRM. Внутренний вызов модуля внутри одного приложения и его доступ к собственному хранилищу не являются интеграцией между сервисами.

| Ответственность общего слоя | Ответственность домена / системы |
|---|---|
| Маршрутизация, аутентификация сервисов, контроль доступа, лимиты | Авторизация конкретного бизнес-действия и допустимые переходы состояния |
| Каталог и версии контрактов, преобразование форматов | Значение полей, источник данных, правила совместимости |
| Координация обменов, сохранение их состояния, доставка, технические повторы, трассировка, карантин | Идемпотентное применение команды и подтверждение результата; бизнес-правила задаются владельцами процесса |
| Адаптация поддерживаемых API систем | Остаток и резерв — WMS; учётный заказ — ERP; профиль — CRM |

Общий слой поддерживает согласованную последовательность и состояние межсистемных обменов. Учётный заказ остаётся в ERP, остаток и резерв — в WMS, профиль — в CRM через её поддерживаемый интерфейс. Customer Data Hub и общий MDM не создаются; платформа не ведёт мастер-профиль клиента. Конкретные правила переходов заказа и компенсаций определяются отдельно; этот ADR не задаёт собственную машину бизнес-состояний. API Gateway дополняется устойчивым транспортом и журналом обработки. Проверка прав в получателе сохраняется после проверки на шлюзе.

| Логический обмен через общий слой | Режим | Владелец результата |
|---|---|---|
| Интернет-магазин → ERP: проверка цены | Запрос с ограниченным ожиданием | ERP / согласованный сервис цен |
| Интернет-магазин → WMS: резерв, проверка результата, освобождение | Команда с идемпотентным ключом и бизнес-подтверждением | WMS |
| Интернет-магазин → ERP: регистрация оплаченного заказа | Сохраняемая команда, отдельное подтверждение регистрации | ERP |
| ERP → WMS: задание с существующим резервом | Сохраняемая команда; единственный инициатор задания — ERP | ERP и WMS |
| ERP/WMS/доставка → интернет-магазин: статусы | Зафиксированные события либо адаптированный восстановимый обмен | Система, выполнившая переход |
| Интернет-магазин → CRM / Loyalty через общий слой | Запросы/команды профиля и бонусных операций; без Customer Data Hub / MDM | CRM — мастер профиля и счёта; Loyalty — бонусные бизнес-операции |
| Источники → BI/рекомендации, история покупки → CRM | События по согласованному контракту, отдельно от записи профиля | Соответствующий владелец данных |

Новые отдельно развёрнутые сервисы e-commerce также используют общий слой для обмена. Внешняя оплата и доставка подключаются через согласованные адаптеры слоя; интерактивная платёжная страница провайдера остаётся пользовательским интерфейсом, а подтверждения серверу проходят контролируемую интеграцию.

Сначала проверить возможности существующей IS-07. Продукт Gateway, брокер и топология выбираются совместно по требованиям, стоимости и компетенциям. Этот ADR не выбирает Kafka, RabbitMQ или отдельный Kubernetes-кластер.

### Координация заказа и восстановление обменов

Платформа связывает сообщения заказа общим online orderId и соответствующими erpOrderId, reservationId и taskId. Она сохраняет ход обмена и подтверждения, чтобы после перезапуска продолжить неподтверждённый шаг, а не создавать новый заказ. Подтверждение приёма сообщения платформой отличается от подтверждения регистрации заказа ERP или принятия задания WMS.

Ошибка доставки истории покупки в CRM или аналитического сообщения не блокирует исполнение уже оформленного заказа. Первая регистрация по ADR-EC-006 по-прежнему требует подтверждения customerId CRM через общий слой до оплаты. Правила удержания резерва, дедлайны отмены и возврата денег задаются отдельно владельцами процесса; транспортный таймаут сам по себе не означает отмену заказа или отказ платежа.

### Надёжность общего слоя и обязанности участников

| Механизм | Общее правило |
|---|---|
| Устойчивая отправка | Бизнес-изменение и намерение отправить сообщение фиксируются атомарно у источника (outbox) либо используются поддерживаемый восстановимый журнал и сверка |
| Идемпотентность | Получатель сохраняет ключ команды/eventId вместе с результатом. Повтор той же операции возвращает прежний результат; изменённое тело с тем же ключом отклоняется |
| Неизвестный результат | Проверить состояние прежней операции или безопасно повторить её с тем же ключом; не создавать новый заказ, платёж, резерв или задание из-за таймаута |
| Повторная доставка | Допускается; потребитель обеспечивает однократный бизнес-эффект. Для событий inbox/регистрация eventId и изменение состояния фиксируются совместно |
| Порядок и версия | Общая оболочка: eventId, eventType, schemaVersion, aggregateId, aggregateVersion, occurredAt, correlationId, payload. Версия применяется в пределах своего агрегата |
| Временная ошибка | Ограниченные повторы с увеличением интервалов и случайным разбросом; один ответственный за технические повторы, без их умножения на каждом слое |
| Ошибка данных или бизнес-отказ | Не повторять как сетевой сбой. Передать согласованный результат владельцу процесса |
| Исчерпаны повторы | Устойчивый карантин/DLQ, алерт и ответственный; replay после устранения причины сохраняет идентификаторы и аудит |
| Сверка | Сопоставлять подтверждённые результаты систем по общим ID; выявлять зависшие обмены, пропуски и расхождения версий |

Отдельная БД адаптера не обеспечивает атомарность с изменением ERP/WMS. Для каждой системы проверяется поддерживаемый механизм фиксации и восстановления результата; если безопасный повтор невозможен, неизвестный результат передаётся на контролируемый разбор. Общая платформа не может обеспечить идемпотентность записи за получателя без его участия.

Сроки хранения ключей и событий покрывают окно повторов и восстановления. Размер буферов, резервирование и RTO/RPO определяются для общей платформы и её участников. Контролируются возраст старейшего сообщения, очередь отправки, задержка потребителей, карантин и результаты сверки. Трассировка использует correlationId и бизнес-ID без полных клиентских контактов и платёжных реквизитов в логах.

Для EC-P-07 платформа обеспечивает доставку исходных фактов в аналитический контур команды 5 и контроль задержек обмена. Подготовка витрин и соблюдение SLA отчётов остаются задачей аналитики; наличие событий само по себе не доказывает решение всей проблемы отчётности. Создание и хранение товарных рекомендаций описаны отдельно в ADR-EC-007.

## Обоснование

Сочетание API и событий позволяет подтвердить резерв в момент оформления и доставлять остальные факты независимо от доступности подписчиков. Общий слой повторно используется всеми командами, а доменные правила остаются у владельцев. Это соответствует API First, слабой связанности и ограничению бюджета без дублирования платформ.

Координация и надёжность доставки относятся к тому же межсистемному обмену, поэтому описаны вместе. Выделение для них отдельных ADR и нового сервиса e-commerce не требуется.

## Связанные требования

| Требование | Как поддерживается |
|---|---|
| REQ-EC-002 | Сквозные идентификаторы, подтверждения и наблюдаемый ход межсистемных обменов заказа |
| REQ-EC-003 | Автоматическая передача и восстановление обменов; целевые ≤10 минут проверяются по отдельно согласованным границам бизнес-процесса |
| REQ-EC-006 | Общий маршрут, каталог, версии и владельцы контрактов |
| REQ-EC-007 | Устойчивая отправка, идемпотентность получателей, ограниченные повторы, карантин и сверка |
| REQ-EC-008 | Независимые доменные контракты вместо изменения каждой отдельной связи |
| REQ-EC-009 | Защищённые каналы, сервисные полномочия и аудит |

## Последствия и риски

Сокращаются отдельные связи, контракты становятся общими. Цена решения — общая зависимость, стоимость эксплуатации и необходимость согласования версий. Для слоя нужны резервирование, рассчитанные лимиты/буферы, изоляция потоков, мониторинг очередей и план восстановления. Отказ аналитического подписчика не должен блокировать резервирование. SLA сайта не получается автоматически из наличия шлюза.

## Проверка и условия пересмотра

| Проверка | Ожидаемый результат |
|---|---|
| Новая интеграция ERP/WMS/CRM | Есть владелец, версия, схема, права, ошибки и маршрут общего слоя; прямой обход отсутствует |
| Недоступна CRM или BI | Ранее оформленный заказ продолжает исполнение; новая регистрация ждёт подтверждения CRM до оплаты; сообщения сохраняются |
| Отказ экземпляра слоя или перегрузка подписчика | Работает согласованный механизм переключения/буферизации; измеряются потери и задержка |
| Сбой после записи, до отправки / после обработки, до подтверждения | Сообщение восстанавливается; повтор не создаёт второй заказ, платёж, резерв или задание |
| ERP обработала команду, ответ потерян | Результат восстанавливается по прежнему ключу и внешнему ID, заказ не создаётся повторно |
| Дубликат, старая версия или разрыв событий | Нет повторного бизнес-эффекта и отката новой версии; пропуск восстанавливается по контракту |
| Карантин и replay | Причина устранена, повтор разрешён и аудируется; исходные ID сохранены |
| Несовместимая версия контракта | Блокируется до выпуска; старый потребитель поддерживается в переходном окне |

Пересмотр нужен, если общий слой не обеспечивает поддерживаемую WMS-команду, восстановимость доставки, безопасность или согласованную нагрузку. Изменение проводится совместно; скрытый прямой обход не является запасным решением.
