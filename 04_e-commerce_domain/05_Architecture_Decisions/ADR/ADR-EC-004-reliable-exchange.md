# ADR-EC-004. Надёжная доставка и однократный бизнес-эффект

| Поле | Значение |
|---|---|
| Версия / дата | 1.0 / 22.10.2026 |
| Статус | Предложено |
| Проблемы | EC-P-04, EC-P-06 |
| Требования | REQ-EC-002/006/007/009 |
| Участники согласования | E-commerce, общий интеграционный слой, ERP/WMS/CRM, эксплуатация и операторы |

## Контекст

As-Is предусматривает ручную проверку неизвестного результата передачи заказа и задания. Простое повторение может создать дубликат, а отсутствие повтора — оставить заказ без исполнения. Между сохранением заказа и публикацией сообщения также возможен отказ.

Общий слой стандартизирует доставку, но не может самостоятельно доказать, что ERP не зарегистрировала заказ или WMS не создала резерв.

## Рассматриваемые варианты

| Вариант | Преимущества | Недостатки / причина отказа |
|---|---|---|
| Ручная обработка всех сбоев | Минимум изменений | Задержки и ошибки сохраняются, REQ-EC-007 не выполняется |
| Бесконечные повторы только на шлюзе | Быстро восстанавливаются простые сетевые сбои | Дубли бизнес-операций, перегрузка получателя, потеря между commit и отправкой |
| Сохраняемая публикация + идемпотентные получатели + ограниченные повторы и сверка | Восстановимость с контролем повторного эффекта | Нужны изменения на обеих сторонах и эксплуатационные процедуры; **выбран** |

## Выбранное решение

Для новых сервисов запись бизнес-изменения и намерения отправить сообщение выполняется одной локальной транзакцией (transactional outbox). Фоновая публикация передаёт сообщения через общий слой. У потребителя регистрация eventId/ключа обработки и изменение локального состояния фиксируются атомарно (inbox). Сбой между обработкой и подтверждением допускает повторную доставку, но не второй бизнес-эффект.

У ERP/WMS нельзя объявлять такую гарантию на основании отдельной БД адаптера. Нужен поддерживаемый механизм в транзакционной границе системы либо полный восстановимый журнал изменений. Если его нет, проектируется переходная сверка с более слабой гарантией и явным ограничением; критичная команда требует идемпотентности/поиска по внешнему ключу в самой системе. При отсутствии обоих средств неизвестный результат направляется на контролируемый разбор, без слепого повтора.

| Механизм | Правило |
|---|---|
| Ключ команды | Стабилен для одной операции над одной версией заказа; область уникальности включает клиента и тип операции |
| Повтор команды | То же тело и ключ возвращают прежний результат; другое тело с тем же ключом отклоняется |
| Создание заказа/задания/платежа | Дополнительная бизнес-уникальность orderId/версии, задания и paymentAttemptId; новый HTTP-запрос не равен новой операции |
| Оболочка события | eventId, eventType, schemaVersion, aggregateId, aggregateVersion, occurredAt, correlationId, payload |
| Порядок | Версия относится к одному агрегату; время не заменяет версию, общего порядка всех событий нет |
| Повторы | Только временные ошибки, ограниченное число/длительность, увеличивающиеся интервалы со случайным разбросом; один ответственный за технические повторы |
| Бизнес-отказ | Нехватка товара, неверная сумма, запрет доступа и ошибки схемы не повторяются как сетевой сбой |
| Исчерпаны повторы | Устойчивый карантин/DLQ, причина, связанный orderId и ответственная команда; алерт и разрешённый replay |
| Replay | После исправления причины, с аудитом, прежними идентификаторами и проверкой идемпотентности; не ручное создание второго заказа |
| Сверка | Заказ/оплата/резерв/ERP/задание сравниваются по внешним ID; выявляются пропавшие события, неизвестные результаты и зависшие процессы |

Потребитель не применяет старую версию поверх новой. Для событий-дельт разрыв версии останавливает применение до восстановления пропуска; для полных снимков допустим переход к новой версии по контракту. Нельзя складывать независимые события заказа и отгрузки как повторное списание одного остатка.

## Наблюдаемость и эксплуатация

| Сигнал | Назначение |
|---|---|
| Возраст старейшего сообщения, outbox backlog, lag потребителя | Видеть задержку даже при низком числе ошибок |
| Число повторов, DLQ и несовпадений сверки | Выявлять потерянное продвижение заказа и нарушения контрактов |
| Время в статусах ожидания, PAYMENT_UNKNOWN/REFUND_PENDING | Передавать оператору конкретную незавершённую операцию |
| Корреляция orderId + correlationId + внешние ID | Проследить путь через общий слой и системы |

Логи не содержат полных клиентских контактов и платёжных реквизитов. Сроки хранения ключей дедупликации, outbox/inbox и событий должны покрывать согласованное окно восстановления и replay. Буфер рассчитывается по нагрузке и допустимому простою; бесконечная очередь не предполагается. Политика RTO/RPO и проверка восстановления утверждаются с эксплуатацией: общий ориентир DOC-17 (4 часа / 1 час) не даёт права терять подтверждённые платежи.

## Обоснование

Сохранение намерения отправки вместе с бизнес-изменением закрывает разрыв между записью и публикацией. Идемпотентность получателя закрывает неопределённость повторной доставки. Карантин и сверка дополняют эти механизмы там, где ошибка не устраняется техническим повтором; один только общий шлюз не обеспечивает всех трёх свойств.

## Последствия и риски

Рутинные временные сбои восстанавливаются автоматически, критичные исключения становятся адресными. Появляются расходы на журналы, буферы, хранение ключей и процедуры сверки. Решение допускает доставку «не менее одного раза»; однократность бизнес-эффекта доказывается локальными ограничениями и идемпотентностью, а не обещанием брокера.

## Проверка и условия пересмотра

Проверить отказ после сохранения до отправки, после применения до подтверждения, дубликаты, нарушенный порядок, разрыв версии, недоступность получателя, исчерпание буфера и replay из карантина. Итог: нет второго заказа/платежа/резерва/задания, подтверждённые операции восстанавливаются, исключения имеют владельца. Отдельно проверить фактический механизм восстановления ERP/WMS, а не только новый сервис.

Если система не поддерживает требуемую уникальность и восстановление результата, пересматривается контракт или этап автоматизации. До устранения ограничения нельзя заявлять гарантированную автоматическую обработку всех ошибок.
