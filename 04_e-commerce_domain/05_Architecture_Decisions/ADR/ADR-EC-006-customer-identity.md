# ADR-EC-006. Единый профиль клиента через Customer Data Hub

| Поле | Значение |
|---|---|
| Версия / дата | 1.1 / 22.10.2026 |
| Статус | Предложено |
| Проблемы | EC-P-05 |
| Требования | REQ-EC-009; AA-RET-02/04, DA-RET-01/04; DA-01/02 из DOC-12, раздел 10 DOC-17 |
| Участники согласования | E-commerce, команда 5 / CRM, маркетинг, владелец идентификации, безопасность |

## Контекст

В As-Is Customer Module передаёт данные клиента в CRM, но единый идентификатор и автоматическая защита от дублей не подтверждены. DOC-06 определяет CRM источником клиента и бонусного счёта. Сайт хранит регистрационные данные, однако это не делает его вторым владельцем корпоративного профиля.

REQ-EC-009 отвечает за защиту данных. Для устранения дублей дополнительно нужны правила идентичности, владения и качества данных; одно шифрование эту проблему не решает.

[Требования Retention](../../../05_retention_domain/01_business_context/Архитектурные_требования.md) задают обязательный Customer Data Hub (AA-RET-02), общий интеграционный слой (AA-RET-04) и CRM как мастер D-02/D-08 (DA-RET-01). Версия 1.1 устраняет расхождение прежнего варианта e-commerce, где MDM откладывался: Hub входит в целевой маршрут первой версии работы с профилем. Это выбор архитектуры нашего домена по опубликованным требованиям команды 5; готовность сервиса и межкомандная приёмка не утверждаются.

## Рассматриваемые варианты

| Вариант | Преимущества | Недостатки / причина отказа |
|---|---|---|
| Независимые профили сайта и CRM, периодическое объединение | Сайт автономен | Дубли сохраняются до сверки, неясно, чья версия правильная |
| Считать email или телефон главным ключом и автоматически объединять | Простая эвристика | Контакты меняются и бывают общими; риск объединить разных людей |
| Upsert CRM через общий слой без обязательного Hub | Стабильные ID и небольшой объём первой версии | Не выполняет AA-RET-02; правила сопоставления остаются в отдельных каналах; отклонён |
| Общий Customer Data Hub перед мастер-системой CRM | Единая дедупликация и контроль изменений для всех каналов, соответствует Retention | Нужны общий контракт, надёжность Hub и идемпотентная запись CRM; **выбран** |

Отдельная MDM-платформа e-commerce не создаётся. Используется общий компонент домена Retention, опубликованный через общую интеграционную платформу; его стоимость учитывается один раз.

## Выбранное решение

Использовать **обязательный Customer Data Hub** как единый вход управления клиентскими данными. Логический маршрут записи профиля: **интернет-магазин → общий интеграционный слой → Customer Data Hub → адаптер CRM в общем слое → CRM**. Сайт не пишет профиль в CRM в обход Hub, в том числе при сбое. Каждый межсервисный переход использует общий слой; Hub не заменяет транспортную платформу.

CRM сохраняет авторитетный профиль и бонусный счёт. Hub проверяет качество данных, разрешает идентичность, ведёт соответствия ID и управляет слияниями; он не становится вторым независимым мастером профиля. Хранилище Hub содержит технические соответствия/алиасы, состояние обработки и при необходимости версионированную проекцию CRM. База профилей на модели Retention в этом варианте должна быть обозначена как хранилище мастер-системы CRM; отдельная физическая БД Hub не получает независимого права менять золотую запись.

Корпоративный customerId выдаётся через Hub после подтверждения создания/нахождения мастер-записи CRM. Уникальность обеспечивает согласованный механизм Hub/CRM, а не локальный генератор каждого канала. При смене контактов ID сохраняется; после слияния старые ID разрешаются через алиасы в один канонический customerId. Отдельный идентификатор учётной записи не подменяет customerId.

| Объект | Владелец / правило |
|---|---|
| Учётная запись и вход | Общая служба идентификации; subject учётной записи отличается от customerId |
| Связь channelAccountId / subject ↔ customerId | Hub ведёт авторитетное соответствие; канал хранит подтверждённую копию с версией |
| ФИО и контакты корпоративного профиля | CRM; создание, изменение и слияние проходят через Hub и общий слой |
| Платёж/заказ | До оплаты обязательна подтверждённая связь customerId; только черновик может ожидать её появления. Для исполнения сохраняется необходимый снимок контакта, а не ссылка на постоянно меняющийся адрес |
| Бонусный баланс и операции | CRM — мастер-счёт; сервис лояльности команды 5 применяет бизнес-правила; команды проходят через управляемый вход Hub |
| Неоднозначное совпадение | Кандидат на проверку, не автоматическое объединение по одному непроверенному полю |

### Контракт профиля и защита от дублей

| Операция Hub | Предлагаемый контракт и результат |
|---|---|
| Найти/создать профиль и связать канал | channelId, channelAccountId/subject, проверенные атрибуты, ключ идемпотентности → customerId, версия и подтверждение связи либо состояние ожидания/проверки |
| Изменить профиль | customerId, ожидаемая версия и разрешённые поля → подтверждённая версия CRM; конфликт не затирает более новую запись |
| Разрешить ID | Подтверждённая связь канала или алиас → канонический customerId с проверкой прав вызывающего |
| Слить исторические дубли | Решение по правилам владельца данных → канонический ID, алиасы, аудит и событие изменения связей |

Это логические контракты, а не утверждение о существующих endpoint. Hub регистрирует запрос устойчиво, CRM применяет запись идемпотентно по внешнему ключу; окончательный успех возвращается после подтверждения мастер-записи. Принятие сообщения в очередь означает только ожидание. После таймаута Hub проверяет результат с тем же ключом, а не создаёт новую карточку. Конкурентные запросы из разных каналов должны проходить одну процедуру сопоставления и контролируемого создания; одной дедупликации HTTP-запросов недостаточно.

Автоматически связывать профили разрешается по подтверждённым правилам идентичности. Общий телефон/email или похожее имя сами по себе не доказывают одного человека. Неоднозначность направляется владельцу данных без автоматического доступа к чужой истории. Авторизация пользователя проверяет владение профилем; знание customerId не даёт доступа.

Изменения связей и подтверждённой версии профиля публикуются через общий слой с eventId, customerId, версией и алиасами по [ADR-EC-001](ADR-EC-001-shared-integration.md). Каналы и аналитика обновляют свои проекции, сохраняют историю заказов и не переносят покупки другому клиенту без контролируемого решения. Полные контакты в событие изменения связи не включаются.

### Граница бонусных операций

AA-RET-02 распространяется также на D-08: команды создания/изменения счёта и бонусных операций проходят через Hub и общий слой. Hub разрешает идентичность и направляет бизнес-команду сервису лояльности команды 5; сервис лояльности атомарно применяет разрешённую операцию к мастер-счёту CRM через поддерживаемый интерфейс. Все межсервисные переходы используют общий слой. Универсальный upsert профиля не имеет поля для произвольного изменения баланса.

Окончательное подтверждение списания/резерва бонусов даёт авторитетная бонусная операция, а не ответ Hub о приёме сообщения и не локальный кэш. Hub не вычисляет бонусы повторно и не создаёт второй ledger. Правила автономного списания POS остаются отдельным открытым стыком G-01; включение Hub само по себе его не закрывает.

### Работа при недоступности Hub или CRM

| Сценарий | Поведение интернет-магазина |
|---|---|
| Известная учётная запись с подтверждённым customerId и действующей проверяемой сессией | Существующий заказ может исполняться; для нового оформления используются разрешённые сохранённые данные. Новые изменения профиля не выдаются за подтверждённые |
| Новая регистрация или отсутствует подтверждённая связь customerId | Запрос сохраняется как PROFILE_LINK_PENDING; оплата и подтверждение нового заказа ждут результата Hub. Новый мастер-профиль локально не создаётся |
| Запрошено изменение профиля | Сохраняется ожидающая команда; действующая версия остаётся прежней до подтверждения CRM через Hub |
| Ошибка/таймаут Hub после отправки | Проверка состояния прежнего запроса через общий слой, без прямого обхода в CRM |
| Не подтверждена бонусная операция | Списание бонусов и новая уменьшенная сумма заказа не подтверждаются; доступные варианты оплаты определяются процессом заказа |

Регистрация/вход из BP-04 сохраняются: это не гостевой checkout. При недоступной идентификации без действующей проверяемой сессии оформление ждёт её восстановления. Для нового клиента Hub/CRM входят в критичную цепочку; доступность этого сценария измеряется отдельно от исполнения ранее оформленного заказа.

### Защита данных

Минимизировать состав сообщений, шифровать каналы, ограничивать доступ ролями и сервисными полномочиями. Оператор видит данные своего назначения, аналитический потребитель — разрешённый набор. Полные контакты и секреты не помещаются в технические логи и общие события. Сроки хранения, удаление/обезличивание, правила согласия на персонализацию и аудит объединений утверждаются владельцами данных и безопасности; конкретные правовые сроки здесь не выдумываются.

## Обоснование

Общий Hub выполняет единые правила идентичности для POS и онлайн, сохраняя CRM мастером. Это выполняет AA-RET-02 без создания отдельной MDM-платформы e-commerce. Идемпотентная запись устраняет дубли от повторов, а межканальное сопоставление отдельно решает задачу идентичности одного человека. Разделение Hub и сервиса лояльности исключает смешение изменения контакта с денежно значимым изменением бонусного счёта.

## Последствия и риски

Профиль и история покупок становятся связными, маршрут записи един для каналов. Нужны надёжность Hub, таблица соответствий, процесс разрешения конфликтов и контроль качества. Новый клиент зависит от готовности Hub/CRM; существующий заказ не откатывается при их отказе. Риск ошибочного слияния важнее формального уменьшения числа карточек; неоднозначность не скрывается автоматизацией. Дополнительный сетевой переход учитывается в SLA и бюджете общей платформы/Retention.

## Проверка и условия пересмотра

| Проверка | Ожидаемый результат |
|---|---|
| Повтор регистрации или одновременный запрос из двух каналов | При однозначно подтверждённой идентичности — одна запись CRM и один customerId через Hub; спорная идентичность направляется на проверку |
| Покупатель сменил контакт | customerId и история сохраняются; изменение подтверждено |
| Два человека используют общий контакт | Нет автоматического доступа к чужому профилю или слияния |
| Hub/CRM недоступны при новой регистрации | PROFILE_LINK_PENDING, оплаты ещё нет, обхода Hub и нового локального мастер-профиля нет; после восстановления запрос применяется один раз |
| Hub/CRM недоступны для уже известного клиента | Ранее созданный заказ исполняется, изменение профиля ожидает подтверждения |
| Ответ CRM потерян после записи | Hub восстанавливает результат прежнего запроса, не создаёт вторую карточку |
| Команда изменения бонусов | Проходит через Hub к сервису лояльности, мастер-счёт изменяется один раз; generic-upsert профиля не меняет баланс |
| Старый профиль объединён с новым | Алиас разрешается однозначно, история и аудит сохранены |
| Запрос чужого customerId | Доступ отклонён; чувствительные данные не попали в логи |

Условия межкомандной приёмки: команда 5 подтверждает контракт Hub/CRM, правила customerId, сопоставления/слияния, полномочия, версии, SLA и восстановление. Обязательность Hub уже выбрана в этом ADR и не откладывается на будущую фазу. Если CRM не поддерживает внешний уникальный ключ или проверку неизвестного результата, нужен совместный адаптационный дизайн; таблица в БД сайта сама по себе не гарантирует отсутствие дублей CRM.
