## Статус и контекст

**Предложено, не утверждено.** Участники: архитектурная команда, владельцы WMS/ERP/платформы, представители каналов. DOC-05 требует использовать платформу для новых обменов; ошибки синхронизации и отсутствие централизованного контроля связаны с WH-P-05.

## Сравнение вариантов

| Вариант | Преимущество | Риск |
| --- | --- | --- |
| Прямые REST-вызовы из каждой системы | Простая первая связь | Рост связанности; потеря изменения при разрыве между commit и вызовом |
| Только периодические файлы | Совместимость со старым ПО | Задержки, ручной контроль, неудобное резервирование |
| Управляемые API + события через платформу | Оперативное подтверждение команд и развязка потребителей | Требует контрактов, устойчивого журнала и эксплуатации |

## Предлагаемое решение

Выбрать третий вариант. Команды, которым нужен бизнес-ответ, выполняются через API с идемпотентностью в WMS. События публикуются после фиксации факта через поддерживаемый transactional outbox или восстановимый журнал изменений. Адаптер преобразует модель и ведёт техническую доставку, но не является владельцем остатка. Доставка допускает повторы, потребители обеспечивают однократный бизнес-эффект.

Outbox в отдельной БД адаптера сам по себе не атомарен с изменением WMS. Поэтому обязательная проверка — сохранение намерения публикации в транзакционной границе WMS либо чтение полного журнала с восстановимым курсором. Если обе возможности отсутствуют, остаётся сверка/пакетный переходный канал с явно более слабой гарантией; принятие целевого SLA откладывается до пересмотра решения.

## Эксплуатационные последствия

Нужны схема версии, единые идентификаторы, ограниченные повторы, карантин, контролируемый replay и сверка. Потребитель применяет версию агрегата и не изменяет Stock по каждому виду бизнес-события. Новый consumer не блокирует транзакцию склада. Простой платформы требует буфера с рассчитанной ёмкостью, а не бесконечной очереди.

Конкретный брокер и продукт Gateway здесь не выбраны: сначала проверяется корпоративная платформа и её возможности. Условия пересмотра — недостижимость durability, пропускной способности, безопасности либо отсутствие согласия общего владельца.
