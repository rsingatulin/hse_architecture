## Контекст и альтернативы

STORE должен работать при разрыве WAN и отдавать закупкам подтверждённые остатки/путь/свежесть. Общий пакет 1.3 закрепляет владельца WMS CENTRAL+STORE. Независимый STORE master у продаж дал бы двух владельцев; только онлайн-запись лишила бы магазин автономности; одна периодическая выгрузка снимка теряет причинность и проверку повторов.

## Решение

Выбран устойчивый локальный журнал + подтверждение WMS через IS-07. movementId уникален для физического движения; journalId/sourceSequence задают порядок. WMS атомарно изменяет запас, inbox, appliedThroughSequence и outbox. Пропуск N блокирует применение N+1 до восстановления; конфликт физического факта сохраняется в reconciliation case, а не отбрасывается. Повтор того же ID/payload безопасен; иной payload — конфликт. Подтверждение границы непрерывное, heartbeat её не продвигает.

Снимок с границей фиксируется атомарно; восстановление магазина накладывает лишь pending выше этой границы. SYNCED/LAGGING/OFFLINE/RECONCILIATION_REQUIRED различаются; OFFLINE определяет WMS по согласованному timeout. План transfer не меняет запас. Центральная отгрузка создаёт товар в пути, частичные STORE-приёмки закрывают его уникальными receiptId/movementId.

## Последствия и условия

Цена — локальная durability, управление журналами/ёмкостью и ручная сверка реальных конфликтов. Нужны тесты INT T-34–40, проверка API и транзакций поставщика WMS, согласование retention/heartbeat/offline-окна. Если гарантии поставщика недостижимы, пересматривается реализация до пилота; запас не переносится в адаптер по умолчанию.
