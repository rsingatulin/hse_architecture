## Измерения и ответственность

| Метрика | Граница измерения | Порог / статус | Ответственный |
| --- | --- | --- | --- |
| Доступность WMS | Успешность согласованной бизнес-операции, включая зависимости | ≥99,5%; период и окно SLA уточнить | Эксплуатация и логистика |
| Отклик UI / критичного API | От действия до результата / от входа в API до бизнес-ответа | ≤3 с / ≤500 мс по DOC-17; профиль и метод уточнить | ИТ |
| Свежесть остатка | От commit версии Stock до применения потребителем | Порог согласует логистика с каналами, не подменять временем ответа API | ИТ и владелец потребителя |
| Ошибки обмена | Число, возраст, причина, количество повторов | Критична любая необъяснимая потеря/двойная операция; временной порог согласовать | Интеграционная поддержка |
| Складской цикл | Принято задание → начат подбор → упаковано → передано | Базовый замер до установления SLA склада | Начальник склада |
| Расхождение учёта | Одинаковые SKU/склад/версия и контрольная точка | Разделять техническую задержку и физическую недостачу | Начальник склада и финансы |
| Очередь и насыщение | Возраст старейшего события, скорость обработки, ресурсы | Предупреждение до исчерпания буфера; пороги по тесту | Эксплуатация |
| Восстановление | Фактическое время и возраст восстановленных данных | RTO ≤4 ч, RPO ≤1 ч как исходный общий предел | Эксплуатация; приёмка логистикой |

Один correlationId связывает запрос, операцию, события и ответы, но eventId/operationId сохраняют собственную идентичность. Панели сотрудника склада показывают состояние задания и следующую допустимую операцию; инфраструктурные детали доступны ИТ.

## Сценарии приёмки архитектурного решения

| ID | Воздействие | Ожидаемый результат | Требование |
| --- | --- | --- | --- |
| QA-01 | Два заказа претендуют на последнюю единицу | Только один подтверждённый резерв; инварианты соблюдены | WH-R-03 |
| QA-02 | Ответ на reserve потерян; повтор с тем же ключом | Возвращён тот же reservationId, объём не увеличился | WH-R-03/09 |
| QA-03 | WMS зафиксировала отгрузку; publisher упал до отправки | После перезапуска событие доставлено из журнала; физическая передача не повторена | WH-R-09 |
| QA-04 | Старое stock.changed пришло после нового | Проекция не регрессирует; пропуск версии обнаруживается | WH-R-02/09 |
| QA-05 | ERP недоступна | Принятые WMS операции сохраняются; внешнее отражение догоняет после восстановления | WH-R-09/10 |
| QA-06 | Одновременные отмена и передача | Допустим один переход по версии; возврат после передачи отдельным процессом | WH-R-05 |
| QA-07 | Истёк ACTIVE-резерв / начат подбор | До подбора освобождается один раз; ALLOCATED автоматически не освобождается | WH-R-03/05 |
| QA-08 | Неизвестный SKU / несовместимая единица | Строка отклонена, запас не искажён, владелец уведомлён | WH-R-01/04 |
| QA-09 | Отказ worker/канала/БД | Раздельно проверены переключение, режим деградации и восстановление | WH-R-10/11 |
| QA-10 | Потеря основной БД | Восстановление копии + журналов, сверка подтверждённых физических операций | WH-R-11 |
| QA-11 | Пиковая нагрузка и потребитель BI тормозит | UI/API отвечают в целевых пределах согласованного профиля; аналитика не блокирует WMS | WH-R-07/12/13 |
| QA-12 | Попытка неавторизованной корректировки | Отказ, запись аудита; легитимная коррекция прослеживается | WH-R-14/19 |
| QA-13 | Откат выпуска после новых операций | Совместимость сохранена, новые движения не потеряны | WH-R-16/18 |
| QA-14 | Контрольный набор задач с оптимизацией/без неё | Сопоставлены время, путь, ошибки; эффект не оценивается на разных профилях | WH-R-06/08 |

Это спецификация будущих испытаний, а не протокол пройденных тестов системы. Сейчас проверяются согласованность моделей, полнота контрактов и расчёты проектных допущений.

## Порядок восстановления

1. Зафиксировать начало инцидента и безопасно ограничить новые команды; сохранить сведения о последней подтверждённой физической операции.
2. Определить отказавшую зависимость и выполнить переключение, если оно безопасно; не запускать второго независимого писателя WMS.
3. При аварийном восстановлении вернуть БД/конфигурацию из проверенной копии и доступных журналов, измерить достигнутые RTO/RPO.
4. Восстановить публикацию/потребление событий с сохранёнными идентификаторами; сверить задания, резервы и остатки с ERP и физическими подтверждениями.
5. Начальник склада и эксплуатация подтверждают возможность продолжить смену. Необъяснимые расхождения расследуются до снятия ограничений по затронутым товарам.
6. Сохранить протокол и обновить инструкции. Периодичность учебного восстановления и сроки копирования задаются эксплуатацией так, чтобы подтвердить цели; одних ежедневных копий недостаточно.
