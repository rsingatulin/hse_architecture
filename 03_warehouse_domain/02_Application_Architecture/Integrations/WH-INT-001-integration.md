## As-Is по исходным документам

DOC-05: ERP ↔ WMS — REST почти в реальном времени; ERP/CRM → BI — суточный ETL; каталог сайта из ERP каждые 15 минут. DOC-16 дополнительно описывает файлы master-товара ERP → WMS и API/пакеты WMS → сайт, одновременно отрицает IS-07. До обследования это альтернативные описания разных объектов/каналов, а не доказанный единый маршрут. Новая модель STORE и удержание оплаченного резерва не добавляются в As-Is.

## Целевая ответственность

Единый межсистемный маршрут — IS-07. Общая платформа включает Gateway, устойчивый транспорт, координацию и адаптеры. Адаптер Warehouse принадлежит интеграционному слою; WMS хранит бизнес-результат, идемпотентность и outbox/поддерживаемый журнал. Техническая БД адаптера не является вторым складским учётом.

| Обмен | Владелец результата | Контракт и смысл |
|---|---|---|
| Справочник товара, ожидаемая поставка | ERP → WMS | WH API-04/12; план не увеличивает остаток |
| Наличие и ранний резерв | WMS → онлайн/ERP | WH API-01/02/13; кеш не подтверждает наличие |
| Удержание после оплаты | WMS по подтверждённому paymentId | WH API-14; гонка с expiry атомарна |
| Учётный заказ и задание | ERP → WMS | Только ERP вызывает WH API-06 с прежним reservationId |
| Отмена | Канал → ERP → WMS | Сначала исключить поздний выпуск задания; затем cancel/release по состоянию |
| Движение магазина | Inventory → WMS | WH API-16; локальный факт + устойчивый журнал, без двойного применения |
| Контакт и сверка магазина | Inventory ↔ WMS | WH API-17/11; свежесть контакта и полнота журнала раздельны |
| Пополнение магазина | ERP → WMS → магазин | WH API-18; transferId связывает план, передачу и частичные приёмки |
| Данные для закупок | Закупки ↔ WMS через IS-07 | INT API-04: текущие количества, путь, расхождения и свежесть без постоянной копии в ERP; EVT-04/25 — сигнал повторного чтения |
| История / аналитика | WMS → BI | Отдельная подписка и контрольный снимок; аналитика не блокирует склад |

## Сценарий онлайн

Канал получает customerId, цены ERP и применимые скидки и отдельное удержание бонусов CRM; WMS резервирует все строки CENTRAL до начала платежа. После проверенного платежа confirm-paid переводит действующий ACTIVE в HELD_FOR_FULFILLMENT. Он не истекает по обычному TTL, но контролируется срок исполнения/разбора. ERP регистрирует оплаченный заказ и выпускает одно задание; WMS связывает его с прежним резервом. При начале подбора — ALLOCATED, при физической передаче — CONSUMED.

Timeout не означает отказ: сначала читается прежний результат. Если expiry подтверждённо победил confirm-paid, предлагается возврат денег без нового автоматического резерва. Refund — ответственность финансов/канала. До освобождения HELD необходимо получить устойчивый запрет позднего создания задания ERP (INT API-21), проверить taskId и завершить допустимую отмену. Отмена сообщения в очереди сама по себе не отменяет выполненное действие.

## Сценарий магазин → WMS → закупки

POS фиксирует чек, Inventory идемпотентно записывает SALE по saleId+lineId и локальное изменение вместе с outbox. Все приёмки, физические возвраты и утверждённые списания имеют отдельные movementId. WMS применяет последовательность журнала, подтверждает непрерывную границу и публикует STORE Stock. EVT-16 POS используется для спроса и финансового учёта, но второй раз количество не уменьшает.

Отсутствие сигнала heartbeat переводит SyncState в OFFLINE. ERP сохраняет последнее известное количество с признаком недостоверной свежести; нулём его не заменяет. Автоматическое решение о пополнении такой локации приостанавливается либо требует явного ручного разрешения по согласованной политике. Reconnect не снимает LAGGING до применения и сверки журнала.

Пополнение 10: план — без изменения запаса; подтверждённая передача CENTRAL −10 и inTransit +10; приёмка 8 — STORE +8/inTransit −8; вторая приёмка 2 — STORE +2/inTransit −2. Повтор первой приёмки не даёт ещё 8. Несовпадение количества сохраняется как расхождение. Онлайн-резерв STORE/самовывоз не вводится этим контуром автоматически.

## Надёжность и переход

Outbox бизнес-системы и inbox потребителя фиксируются в локальных транзакциях. Один владелец технических повторов на шаг; backoff, deadline, карантин, управляемый replay с прежними ID. Для UNKNOWN legacy должен предоставить поиск результата по бизнес-ID. Если ни атомарный outbox, ни полный журнал WMS недоступны, гарантии пересматриваются до пилота, не имитируются отдельной БД адаптера.

Новая версия схемы включается с одним бизнес-писателем. Shadow используется только для чтения/сверки. Ключи дедупликации и курсоры восстанавливаются вместе с данными. [Каталог](../APIs/WH-API-001-catalog.md), [стыки](../../07_Project_Management/WH-PM-002-coordination.md), [приёмка](../../04_Technology_Architecture/Monitoring/WH-OPS-001-operations.md).

ERP не сохраняет текущие остатки из ответа или EVT-04/25 в таблице/постоянном кэше. При недоступности WMS автоматическое пополнение приостанавливается; в ERP остаются сформированные планы и учётные документы. Аналитика BI и оперативная копия магазина используют собственные разрешённые проекции. Проверка этой границы — INT T-41 / QA-25.
