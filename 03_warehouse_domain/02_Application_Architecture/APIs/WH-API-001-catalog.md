## Статус и общие правила

Контракты ниже — проект To-Be, а не перечень работающих endpoint. Публичного интернет-доступа к WMS нет. Логическая база `/warehouse/v1` публикуется Integration Platform; реализация преобразует запросы в поддерживаемый интерфейс WMS.

Все команды используют аутентифицированного клиента, `X-Correlation-Id` и `Idempotency-Key`. Ключ уникален для клиента и типа операции; WMS сохраняет его вместе с результатом. Повтор одинаковой команды возвращает прежний результат, изменённого тела с тем же ключом — `409`. Для важных переходов передаётся ожидаемая версия объекта (`If-Match` либо `expectedVersion`). Длительность хранения ключей должна покрывать окно повторов и восстановления; до согласования срок не фиксируется.

## Каталог операций

| ID | Метод и относительный путь | Потребитель → исполнитель | Вход / результат | Ошибки и бизнес-правило |
| --- | --- | --- | --- | --- |
| API-01 | `GET /stocks?warehouseId=&productId=` | ERP/онлайн → WMS | Идентификаторы → onHand, reserved, blocked, available, version, asOf | `404` неизвестный товар/склад; результат чтения не является резервом |
| API-02 | `POST /reservations` | ERP/онлайн → WMS | orderId, warehouseId, строки → reservationId, status, expiresAt | `201`; `409` нехватка/конфликт; все строки атомарно, частичное принятие в базовом варианте запрещено |
| API-03 | `POST /reservations/{id}/release` | Владелец заказа → WMS | Причина, expectedVersion → результат освобождения | Повтор освобождения безопасен; после начала подбора нужна управляемая отмена задания, не простое освобождение |
| API-04 | `PUT /expected-receipts/{externalId}` | ERP → WMS | purchaseId, версия, ожидаемые строки → подтверждённая версия | `200/201`; устаревшая версия `409`; товар должен существовать |
| API-05 | `POST /receipts/{id}/confirm` | Разрешённый складской клиент → WMS | Принятые/отклонённые строки, ячейки, основание → receiptId, movementIds | Факт приёмки не создаётся из одной ожидаемой поставки; требуется подтверждение сотрудника |
| API-06 | `POST /fulfillment-tasks` | ERP → WMS | orderId, reservationId, получатель → taskId, state | `201`; один активный набор исполнения для заданной версии заказа; чужой/просроченный резерв отклоняется |
| API-07 | `GET /fulfillment-tasks/{id}` | ERP/онлайн → WMS | taskId → состояние, версия, исключения | `404`; просмотр не изменяет задание |
| API-08 | `POST /fulfillment-tasks/{id}/cancel` | Владелец заказа → WMS | Причина, expectedVersion → отменено/ожидает возврата отобранного | После передачи `409`: нужен отдельный процесс возврата; при начатом подборе `202` до завершения физического возврата |
| API-09 | `POST /shipments/{id}/confirm-handover` | Уполномоченный сотрудник склада → WMS | taskId, подтверждение получателя, expectedVersion → отгрузка | Однократная фиксация передачи; оплата и доставка до клиента здесь не подтверждаются |
| API-10 | `POST /inventory-counts/{id}/approve` | Начальник склада → WMS | Основание, версия снимка, результаты → adjustmentIds | Проверка прав и отсутствия конфликтующих движений; повтор не удваивает корректировку |
| API-11 | `GET /stock-snapshots/{id}/items?cursor=` | ERP/BI → WMS | Согласованный snapshotId, курсор → строки одной версии/границы времени | Пагинация стабильного снимка; разные снимки нельзя смешивать |
| API-12 | `PUT /products/{productId}` | ERP → WMS | Мастер-поля, unitCode, sourceVersion → принятая версия | Склад не меняет цену/артикул как мастер-источник; старую версию отклоняет |

API-05/09/10 — границы прикладных функций для разрешённых складских клиентов; имеющийся интерфейс WMS может использовать внутреннюю реализацию без внешнего сетевого вызова. Обход прав через сервисную учётную запись не допускается.

## Контракт атомарного резервирования

```json
{
  "orderId": "ORD-EXAMPLE-001",
  "warehouseId": "WH-CENTRAL",
  "lines": [{"productId": "SKU-001", "quantity": 1}],
  "requestedExpiresAt": "2026-10-04T15:00:00Z"
}
```

Дата и идентификаторы — только пример формата. Срок определяет согласованная политика WMS; клиент не может произвольно продлить резерв. Результат содержит `reservationId`, `expiresAt`, `version` и состояние. При потере ответа клиент повторяет **тот же** ключ; создание нового ключа может означать новый бизнес-запрос и потому дополнительно контролируется уникальность активного резерва по orderId/версии.

## События

| Событие | Агрегат и полезная нагрузка | Потребители |
| --- | --- | --- |
| `warehouse.stock.changed.v1` | Stock: productId, warehouseId, актуальные количества и версия | ERP, онлайн, BI |
| `warehouse.receipt.confirmed.v1` | Receipt: purchaseId, принятые строки, movementIds, расхождения | ERP/закупки, BI |
| `warehouse.reservation.changed.v1` | Reservation: orderId, состояние и expiresAt | Владелец заказа |
| `warehouse.task.state-changed.v1` | FulfillmentTask: orderId, состояние, reasonCode | ERP, онлайн, согласованный потребитель доставки |
| `warehouse.shipment.handed-over.v1` | Shipment: taskId, получатель, время, строки | ERP, онлайн/розница, BI |
| `warehouse.inventory.adjusted.v1` | InventoryCount: утверждающий, основание, movementIds | ERP, аудит/BI |

Общая оболочка: `eventId`, `eventType`, `schemaVersion`, `aggregateId`, `aggregateVersion`, `occurredAt`, `correlationId`, `payload`. Версия относится к указанному агрегату; версия Shipment не используется для упорядочения Stock. Денормализованный остаток обновляет только событие Stock, остальные факты не списывают его повторно у потребителя.

## Совместимость, качество и безопасность

| Аспект | Правило | Приёмочная проверка |
| --- | --- | --- |
| Схема | Обязательные поля, типы, единица измерения и enum описываются в OpenAPI/схемах событий при реализации | Неверное тело отклонено до изменения WMS |
| Версии | Ломающая правка — новая версия; переходное время поддерживает обе версии с одним источником записи | Старый потребитель проходит контрактную проверку |
| Доступ | Чтение, reserve, execute, inventory-approve — разные полномочия | Онлайн-клиент не может подтвердить физическую передачу |
| Ошибка | `400/422` неверные данные; `401/403` доступ; `409` конфликт; `429/503` временная недоступность | Повторы только для временных ошибок и с тем же ключом |
| Время | UTC-время события + asOf; версия определяет порядок, часы не заменяют версию | Задержанное событие не откатывает новое состояние |
| Производительность | Критичные API ≤500 мс по DOC-17; состав критичных операций и профиль согласуются | Отдельно измеряются ответ API, доставка события и время физической операции |

Требования свежести и сроков повторов пока не определены источниками; их утверждают владельцы до приёмки.
