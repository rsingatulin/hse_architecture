
### ADR-004

**Сохранение базовой технологической архитектуры с ограниченным расширением интеграционной инфраструктуры**

**Статус** Принято

**Контекст** В рамках перехода от As-Is к To-Be архитектуре домена «Закупки» RetailMax предусматривается автоматизация планирования потребности, сокращение количества ручных операций и использование технологий искусственного интеллекта для прогнозирования спроса (DOC-08, AI-01).

Для реализации целевого процесса предполагается создание сервиса «Планирование и прогнозирование» (Procurement Planning Service), который будет использовать данные о продажах, складских остатках и других факторах, влияющих на потребность в закупках.

В соответствии с ADR-003 для обеспечения оперативного поступления данных выбран событийный механизм взаимодействия с использованием брокера сообщений Kafka / RabbitMQ. Если такой брокер отсутствует в существующей инфраструктуре RetailMax, его внедрение представляет собой расширение технологической архитектуры.

При этом основные изменения проекта затрагивают бизнес-процессы, прикладные сервисы и интеграционные взаимодействия. Полная модернизация технологической платформы не требуется, поскольку существующие инфраструктурные компоненты могут продолжать использоваться для размещения и эксплуатации корпоративных приложений.

Таким образом, необходимо определить целесообразность сохранения базовой технологической архитектуры с возможностью её ограниченного расширения для поддержки событийного обмена и интеллектуального прогнозирования.

**Рассматриваемые варианты**

**Вариант 1: Сохранение технологической архитектуры без изменений** Новые функциональные возможности реализуются исключительно с использованием существующих технологических компонентов и интеграционных механизмов.

- **Преимущества:** Минимальные затраты на инфраструктуру; отсутствие необходимости внедрения новых технологий; сохранение существующих процессов эксплуатации.
- **Недостатки:** Ограниченные возможности организации событийного обмена при отсутствии брокера сообщений; риск несоответствия требованиям ADR-003; возможное снижение оперативности получения данных для прогнозирования.

**Вариант 2: Сохранение базовой технологической архитектуры с ограниченным расширением интеграционной инфраструктуры** Существующая технологическая платформа сохраняется, однако дополняется необходимыми компонентами для реализации новых функциональных требований. В частности, предусматривается внедрение или использование корпоративного брокера сообщений Kafka / RabbitMQ для событийного взаимодействия между информационными системами.

- **Преимущества:** Сохранение существующей технологической платформы; соответствие требованиям ADR-003; возможность получения данных в режиме, близком к реальному времени; повторное использование существующих инфраструктурных компонентов; снижение затрат и рисков по сравнению с полной модернизацией.
- **Недостатки:** Дополнительные затраты на развёртывание и сопровождение брокера сообщений при его отсутствии; увеличение сложности интеграционной инфраструктуры; необходимость обеспечения мониторинга, отказоустойчивости и гарантированной обработки событий.

**Вариант 3: Полная модернизация технологической архитектуры** Пересмотр существующей технологической платформы с изменением принципов размещения приложений, организации интеграций, хранения данных и эксплуатации сервисов.

- **Преимущества:** Возможность комплексной оптимизации технологической инфраструктуры; создание единой платформы с учётом перспективных требований.
- **Недостатки:** Значительные финансовые и временные затраты; высокие риски миграции; необходимость изменения существующих интеграций; увеличение сложности проекта без прямой необходимости для достижения его бизнес-целей.

**Выбранное решение** **Вариант 2** (Сохранение базовой технологической архитектуры RetailMax с ограниченным расширением интеграционной инфраструктуры).

**Обоснование** Основная цель проекта заключается в совершенствовании бизнес-процессов закупок, сокращении ручных операций и повышении качества планирования за счёт автоматизации и применения AI (DOC-08, AI-01).

Существующая технологическая архитектура рассматривается как достаточная основа для реализации целевого решения и не требует полной модернизации.

Вместе с тем реализация событийного взаимодействия, предусмотренного ADR-003, может потребовать внедрения брокера сообщений Kafka / RabbitMQ, если соответствующий компонент отсутствует в действующей инфраструктуре.

Такое расширение носит локальный характер и не предполагает изменения базовых принципов размещения приложений, хранения данных и эксплуатации корпоративных систем.

Использование корпоративной Integration Platform позволяет централизовать межсистемные взаимодействия и избежать создания независимых интеграционных механизмов внутри домена «Закупки».

Выбранный подход обеспечивает баланс между сохранением существующих технологических решений и необходимостью поддержки новых функциональных возможностей, включая AI-прогнозирование.

**Последствия**

- **Положительные:** Сохранение базовой технологической архитектуры; отсутствие необходимости масштабной модернизации инфраструктуры; обеспечение событийного взаимодействия в соответствии с ADR-003; возможность внедрения AI-прогнозирования; снижение затрат и технологических рисков по сравнению с полной переработкой архитектуры.
- **Отрицательные:** Возможное усложнение интеграционной инфраструктуры; дополнительные затраты на развёртывание и сопровождение брокера сообщений; необходимость обеспечения мониторинга и отказоустойчивости новых компонентов; зависимость оперативности прогнозирования от корректности и своевременности доставки событий.
