### ADR-003
**Стратегия хранения данных для ограниченных контекстов (Bounded Contexts) домена «Закупки»**

**Статус**
Принято

**Контекст**
В рамках домена «Закупки» выделено несколько ограниченных контекстов: *Управление поставщиками*, *Управление заказами*, *Контроль исполнения*. В текущей архитектуре (As-Is) все данные хранятся в единой централизованной БД корпоративной ERP (DB-01, DOC-07). Это приводит к тому, что бизнес-логика разных контекстов переплетена на уровне SQL-запросов и JOIN-таблиц, что делает систему крайне хрупкой и сложной для изменения (DOC-15, проблемы As-Is).

**Рассматриваемые варианты**

**Вариант 1: Общая база данных с разделением на схемы (Shared Database, Schema-per-service)**
Все новые микросервисы домена «Закупки» подключаются к существующей единой БД, но каждый сервис работает только со своим набором таблиц (схемой).
*   **Преимущества:** Легкость миграции с As-Is; возможность использовать привычные распределенные транзакции (ACID) и JOIN-запросы между контекстами.
*   **Недостатки:** Сохраняется скрытая связанность (разработчики могут случайно сделать JOIN через БД); блокировки на уровне СУБД; невозможность независимого масштабирования и выбора типа БД под конкретную задачу.

**Вариант 2: Изолированная база данных для каждого Bounded Context (Database-per-Context)**
Каждый ограниченный контекст владеет своей собственной, физически изолированной базой данных (или независимым кластером). Доступ к данным другого контекста только через API.
*   **Преимущества:** Истинная слабая связанность; независимое масштабирование и резервное копирование; возможность использовать PostgreSQL для транзакций заказов и, например, документную БД для аналитики поставщиков; строгое соблюдение принципов DDD.
*   **Недостатки:** Сложность обеспечения целостности данных между контекстами; дублирование некоторых справочных данных (например, ID товара).

**Выбранное решение**
**Вариант 2** (Database-per-Context).

**Обоснование**
Для достижения архитектурной гибкости и скорости вывода новых функций (DOC-08, Цель 2 и 5) необходимо устранить «бутылочное горлышко» единой базы данных. Принцип 3 (Единый источник достоверных данных, DOC-13) требует, чтобы каждый контекст был владельцем своих данных. Изоляция БД физически запрещает нарушение границ контекстов.

**Последствия**
*   **Положительные:** Команды могут разворачивать изменения в своих сервисах независимо; повышение отказоустойчивости (падение БД заказов не остановит сервис поставщиков); упрощение будущего масштабирования.
*   **Отрицательные:** Сложности при управлении сквозными бизнес-транзакциями (например, при согласовании оплаты и резервировании товара). 

**Связанные требования**
| Требование | Связь |
|---|---|
| DA-01 (Единый источник данных) | Четкое закрепление владельца данных за каждым контекстом и его БД. |
| DA-02 (Снижение дублирования) | Дублирование контролируется на уровне API |
| AA-02 (Сервисный подход) | Сервисы становятся полностью независимыми, включая уровень хранения. |
| Принцип 3 (Единый источник) | Реализация принципа на физическом уровне инфраструктуры. |
