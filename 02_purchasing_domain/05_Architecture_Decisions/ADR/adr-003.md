### ADR-003
**Механизм получения данных о продажах и остатках для сервиса прогнозирования**

**Статус**
Принято

**Контекст**
Сервис «Планирование и прогнозирование» (Procurement Planning) нуждается в непрерывном потоке данных о фактических продажах (из POS/Интернет-магазина) и текущих остатках (из WMS) для работы алгоритмов прогнозирования спроса. В As-Is аналитические данные обновляются раз в сутки через пакетную ETL-выгрузку (DOC-05, INT-06; DOC-16, INT-005), что делает прогнозирование невозможным и приводит к дефициту или затовариванию.

**Рассматриваемые варианты**

**Вариант 1: Синхронный опрос (Polling) по REST API**
Сервис планирования по расписанию (например, раз в час) делает массовые запросы к API WMS и ERP для получения среза остатков и продаж.
*   **Преимущества:** Относительная простота реализации на первом этапе; не требует внедрения брокеров сообщений.
*   **Недостатки:** Создает паразитную нагрузку на базы данных WMS и ERP; данные все равно поступают с задержкой; жесткая связанность сервисов (нарушение Принципа 7).

**Вариант 2: Событийная архитектура (Event-Driven Architecture)**
Системы-источники (WMS, POS, Интернет-магазин) при каждом факте продажи или изменения остатка публикуют доменное событие (например, `SaleCompleted`, `InventoryAdjusted`) в централизованный брокер сообщений (Kafka). Сервис планирования подписывается на эти события и обновляет свою внутреннюю модель.
*   **Преимущества:** Данные поступают практически в реальном времени; полная слабая связанность (источник не знает о потребителе); масштабируемость; основа для внедрения AI (DOC-08, AI-01).
*   **Недостатки:** Требует настройки и администрирования брокера сообщений; необходимость решения проблемы гарантии доставки событий.

**Выбранное решение**
**Вариант 2** (Использование брокера событий Kafka / RabbitMQ).

**Обоснование**
Целевая архитектура (DOC-08, Цель 4) требует аналитики в режиме, близком к реальному времени. Событийная модель является стандартом для современных микросервисных архитектур и напрямую реализует Принцип 7 (Слабая связанность) и Принцип 9 (Cloud Native) из DOC-13. Это критически важно для работы будущих AI-моделей прогнозирования.

**Последствия**
*   **Положительные:** Прогнозирование потребности становится точным и динамичным; снижается уровень неликвидов и дефицита; сервис планирования не блокирует работу складских и кассовых систем.
*   **Отрицательные:** Усложнение технологического стека; ИТ-отделу потребуются новые компетенции для поддержки Kafka.

**Связанные требования**
| Требование | Связь |
|---|---|
| DA-03 (Доступность аналитических данных) | Обеспечение данных для прогнозной аналитики без задержек. |
| AA-01 (Снижение связанности) | Потребители данных не связаны с источниками напрямую. |
| AI-01 (Использование AI) | Непрерывный поток событий необходим для обучения и работы ML-моделей. |
