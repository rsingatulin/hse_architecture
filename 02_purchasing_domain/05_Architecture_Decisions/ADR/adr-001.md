### ADR-001
**Выбор подхода к интеграции с внешними системами поставщиков**

**Статус**
Принято

**Контекст**
В текущей архитектуре (As-Is) обмен данными с поставщиками (заказы, подтверждения, уведомления об отгрузке) осуществляется преимущественно через ручной файловый обмен или FTP (DOC-05, INT-003; DOC-16, INT-003). Это приводит к задержкам, ошибкам ручного ввода и отсутствию прозрачности статуса поставок. Руководителю отдела закупок (DOC-11) критически не хватает автоматизации. Необходимо спроектировать целевой механизм взаимодействия с поставщиками для сервиса «Интеграция с поставщиками» (Supplier Integration Service).

**Рассматриваемые варианты**

**Вариант 1: Создание B2B-портала для поставщиков**
Разработка веб-портала, где поставщики авторизуются, вручную просматривают заказы, подтверждают их и загружают данные об отгрузке.
*   **Преимущества:** Не требуется сложная техническая интеграция с ERP-системами самих поставщиков; быстрый старт для мелких контрагентов.
*   **Недостатки:** Сохраняется «человеческий фактор» и ручной ввод; поставщики не хотят заходить на десятки порталов разных клиентов; не решает проблему автоматизации (нарушает Принцип 5 DOC-13).

**Вариант 2: API-шлюз и событийная модель (REST API)**
Внедрение специализированного шлюза, который принимает и отправляет стандартизированные сообщения (REST API) напрямую в ERP-системы крупных поставщиков. Для мелких поставщиков — упрощенный API или вебхуки.
*   **Преимущества:** Полная автоматизация обмена; мгновенное обновление статусов; соответствие принципу API First (Принцип 4 DOC-13); снижение трудозатрат менеджеров.
*   **Недостатки:** Требует затрат на маппинг форматов данных и онбординг поставщиков; не все контрагенты имеют готовые API.

**Выбранное решение**
**Вариант 2** (основной упор на API для ТОП-50 поставщиков, генерирующих 80% объема).

**Обоснование**
Стратегия цифровой трансформации (DOC-08, Цель 3) направлена на сокращение ручных операций. Вариант 2 обеспечивает слабосвязанную интеграцию (Принцип 7 DOC-13) и формирует единый стандарт обмена. Это позволит реализовать автоматическое закрытие заказов и мгновенное уведомление WMS о плане поставок.

**Последствия**
*   **Положительные:** Сокращение времени обработки заказа поставщика с 2 дней до нескольких минут; исключение ошибок ручного ввода; появление возможности строить точную аналитику по надежности поставщиков в реальном времени.
*   **Отрицательные:** Необходимость выделения ресурсов на разработку команды интеграции и проведение переговоров с ИТ-департаментами ключевых поставщиков для настройки API.

**Связанные требования**
| Требование | Связь |
|---|---|
| AA-01 (Снижение связанности) | Прямое API-взаимодействие через шлюз заменяет точечные файловые обмены. |
| BR-03 (Автоматизация) | Устранение ручного ввода данных о поставках. |
| Принцип 4 (API First) | Все новые интеграции строятся на базе контрактов API. |
