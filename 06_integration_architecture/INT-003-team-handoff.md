# INT-003 — передача модели командам и переход на To-Be

**Версия 1.0 · 12.11.2026 · Пакет команды интернет-магазина для совместного ревью**

## 1. Как встроить модель в собственные схемы

В C4 каждого домена Integration Platform показывается одной общей системой с пометкой IS-07. Доменные адаптеры — части этого слоя; отдельный доменный Gateway не означает отдельную корпоративную платформу. На детальных схемах API, команды и события подписываются разными типами связей и ссылками `INT API-xx` / `INT EVT-xx`. Если транспорт скрыт для читаемости, добавляется явная пометка «все межсистемные связи через IS-07» и ссылка на INT-C4-002.

Для каждого междоменного объекта команда указывает мастер-систему и назначение своей копии. Собственная БД домена не соединяется с чужой БД. Бизнес-этап «проверить резерв» получает ответ WMS, а не ответ брокера. В sequence нужно показать как минимум основной путь, UNKNOWN при потере ответа и восстановление с прежним ключом.

Интернет-магазин координирует общий архитектурный пакет. Ответственность за разработку ERP/WMS/CRM и эксплуатацию общей платформы этим не переносится целиком на e-commerce. Персональные исполнители и оценки назначаются участниками после согласования границ.

До решения самовывоз не включается в первую волну.

## 3. Решения для совместного ревью

Каждая строка содержит предлагаемый вариант: командам не нужно проектировать стык заново. Статус всех новых пунктов — «предложено», согласующие ещё не подтвердили их.

| ID | Предлагаемое решение | Кто принимает | Условие принятия |
|---|---|---|---|
| D-01 | Все новые обмены через один IS-07; совместимые API + события; отдельный MDM отсутствует | Все команды, ИТ | Обновлён маршрут на каждой To-Be-схеме; Retention пересмотрел AA-RET-02. |
| D-02 | WMS `confirm-paid` удерживает действующий резерв без обычного TTL; после timeout сначала проверка результата | WMS, ERP, e-commerce, финансы | Согласован enum/версия схемы и тест гонки expiry; определён deadline разбора. |
| D-03 | Поздний подтверждённый платёж при доказанно истёкшем резерве → возврат; без автоматического нового резерва | E-commerce, финансы, WMS | Определены сроки/права refund; тест потерянного ответа и повторного callback |
| D-04 | До release оплаченного резерва исключить поздний выпуск задания ERP; cancellation проверяется в WMS | ERP, WMS, e-commerce | API-21, условие уникальности задания и тест reorder cancel/create. |
| D-05 | Офлайн POS продаёт без списания бонусов; авторитетный hold до онлайн-списания; ответ о деградации в 200 мс | Продажи, Retention, коммерция | Принята политика цены offline и таймаут полного пути. |
| D-06 | CENTRAL ведёт WMS; STORE выделяется отдельно, предлагаемый владелец — Inventory команды 1 | Продажи, Warehouse, логистика | Однозначный владелец каждой локации и transferId. |
| D-07 | Базовая цена ERP; единая функция Pricing использует версии акций Campaign, отдаёт quote | Коммерция, ERP, продажи, Retention | Подтверждено место выполнения, владелец и срок quote. |
| D-08 | Loyalty начисляет по `erp.sale.posted`, сторнирует по `erp.sale.reversed`; POS и онлайн сохраняют операционную историю отдельно | ERP/финансы, продажи, Retention | Один финансовый факт на покупку, выведен старый обработчик начислений; определены условия финансового признания |
| D-09 | Приёмка WMS может быть частичной; только Stock меняет проекции количества | Закупки, Warehouse, аналитика | Общие purchaseId/receiptId/movementIds. |
| D-10 | Оперативные факты — события; историческая загрузка/сверка — отдельный управляемый поток | Закупки, Retention, платформа | Подписаны границы watermark, свежесть и дата выключения старого начисляющего потока. |
| D-11 | Прогноз спроса, предложение закупки, прогноз нагрузки склада и рекомендации — разные выходы; общие исходные витрины | Закупки, Warehouse, Retention | Владельцы результата и горизонты, размещение Procurement Planning. |
| D-12 | Разделить SLO просмотра и checkout либо поднять доступность WMS/CRM; определить перцентили и границы 5 с / 10 мин | Все владельцы, эксплуатация | Проверяемый бюджет и профиль нагрузки; INT-001 §10 |

Модели D-02/03/04 составляют один сквозной вариант; нельзя принять только early reserve и убрать удержание/компенсацию из плана. Также нельзя перенести начисление на ERP-факт, оставив активным старое начисление по SaleCompleted.

## 4. Этапы перехода

| Этап | Работы | Условие завершения |
|---|---|---|
| M0. Общие контракты | Инвентаризация IS-07 и legacy API; согласование D-01–12; ID, схемы, права, сроки хранения, сценарии и единая смета | Для критичного пути есть владельцы/версии, WMS/ERP/CRM подтверждают необходимые транзакции; выбрана трактовка NFR |
| M1. Основа платформы | Gateway, устойчивый транспорт и координация, адаптеры, outbox/journal, operation status, DLQ, мониторинг; контрактные стенды | Сбой до/после записи не теряет действие и не создаёт дубль; работает восстановление |
| M2. Читающие проекции | Начальная загрузка каталога/Stock/customer links с boundary, затем поток; теневое сравнение с прежними копиями | Сверка ключей/версий/количеств; теневой поток не создаёт резервов, оплат или бонусов |
| M3. Пилот операций | Ограниченная группа заказов центрального склада; удержание/ERP/задание/доставка/компенсации. Отдельные пилоты PO и POS/CRM | Пройдены тесты INT-004, подтверждены сроки и dashboard, назначены дежурные |
| M4. Расширение и отключение старых путей | Переключение по каналу/операции, перенос аналитики/начислений, удаление лишних интеграций после сверки | Один активный писатель на каждый бизнес-эффект; старые маршруты выключены и откат отрепетирован |

Это порядок зависимостей, а не оценённый календарь. Сроки и стоимость назначаются после M0; команда e-commerce не обязуется за чужую разработку. Общая платформа учитывается один раз в бюджете проекта.

## 5. Переключение и откат

Для каждой операции хранится версия маршрута. Существующий заказ продолжает свой закреплённый сценарий; новый маршрут применяется к новым заказам после контрольной точки. Shadow допустим для чтения/сверки, но не для двойной оплаты, двойного задания или двойного начисления.

Откат останавливает приём новых операций в проблемный маршрут, сохраняет журнал и завершает/урегулирует уже принятые. Переключение новых операций возможно только на путь с теми же бизнес-ID и защитой от дублей. Нельзя переключить оплаченный заказ на старый поток, который резервирует заново. Перед выключением старого подписчика проверяются исходящие очереди и незавершённые финансовые/бонусные операции.

## 6. Что должна вернуть каждая команда

Команда подтверждает список потребляемых/публикуемых контрактов с версиями, владельца данных и реализации, изменения своих схем, принятые решения D-xx либо конкретные возражения, зависимые задачи и результаты совместных тестов. После этого координатор обновляет общий пакет и статусы согласования. Наличие этого документа не заменяет подтверждения команд; текущий статус пакета — проект для ревью.
