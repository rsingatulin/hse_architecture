# INT-004 — сквозная приёмка интеграции To-Be

**Версия 1.2 · 12.11.2026 · План проверок для реализации**

Проверки ниже — критерии будущей приёмки, а не отчёт об испытании работающих систем. Проверка самого пакета (ссылки, рендеринг, схемы JSON) отражается отдельно в [отчёте сборки](output/validation.txt).

## 1. Основные сценарии

| T-31 | Товары на 1 000 ₽, подтверждённая персональная скидка 100 ₽ и бонусное списание на 50 ₽ | API-28 не меняет бонусный баланс; отдельный API-17 подтверждает 50 ₽. | T-36 | В журнале пропущен N, доставлен N+1; ответ WMS для N потерян | Граница не перескакивает через пропуск; повтор N возвращает прежний эффект. | T-38 | Возврат денег без товара; отдельно физический возврат, списание и инвентаризация | Деньги не увеличивают остаток. ## 2. Транспорт, данные и безопасность

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| T-19 | Остановить источник после бизнес-коммита до публикации; consumer после коммита до ACK | Outbox восстанавливает отправку, inbox предотвращает повтор; ключи и бизнес-данные согласованы |
| T-20 | Дубликаты и обратный порядок Stock v8/v7; пропуск факта Receipt | Stock остаётся v8; Receipt восстанавливается через журнал/сверку, не отбрасывается как «старая версия заказа» |
| T-21 | Исторический снимок + события на границе watermark | Нет потери и удвоения; импорт снимка не запускает начисления и реальные складские операции |
| T-22 | Ошибка схемы, 503 и бизнес-отказ | Неверная схема — карантин, 503 — ограниченный retry, бизнес-отказ — конечный результат; нет бесконечного повторения |
| T-23 | Replay DLQ через время жизни резерва/подтверждений цены и скидки; replay v1 и v2 | Сохранены ID; проверены актуальные бизнес-условия и совместимость; стоимость уже оплаченного заказа не пересчитана; нет второго бизнес-эффекта |

| T-25 | Отказ экземпляра Gateway/координатора/транспорта; восстановление backup | Подтверждённый приём не исчезает при оговорённом отказе; один исполнитель шага; сверка источников до replay |
| T-26 | Подмена customerId, online confirm-handover, BI create task, неподписанный webhook | Отказ по правам/подлинности, аудит; нет чужих данных и изменений |

| T-29 | Уведомление перевозчика раньше WMS handover | Сохранить факт для сверки, не фальсифицировать складскую передачу; выявить несогласованную цепочку |
| T-30 | Пилотный peak-профиль + отключение зависимости | Измерены границы API/операции, p95/p99, свежесть, буфер и восстановление; у POS проверен общий бюджет получения персональной скидки и бонусного подтверждения, а не 200 мс на каждый вызов. SLO подтверждены по определённым сценариям, а не только наличию компонентов |

## 3. Что сохранять как доказательства

Для каждого теста: версия контракта/сценария, входные business ID и ключи, точка внесения сбоя, наблюдённые подтверждения ERP/WMS/CRM/провайдера, число бизнес-эффектов, состояние очередей/IntegrationRun, время восстановления и итог сверки. Для магазина также storeId/locationId, movementId/transferId, journalId и границы журнала, статус/остаток в WMS и в проекции закупок. В логах не должно быть полных контактов или платёжных реквизитов.

Наиболее важные инварианты: один резерв и одно исполнение на orderId/orderVersion; не более одного подтверждённого списания на paymentAttemptId; один bonus effect на исходную покупку/операцию; единственный писатель количества по locationId; сохранность всех receiptId/movementId. В онлайн нет запуска оплаты до подтверждённого customerId, цен ERP и резерва; персональная скидка подтверждена для этого клиента/состава либо покупатель явно выбрал допустимый режим без неё. Скидка и бонусы отражены отдельно, согласованный итог сохранён и не изменяется после оплаты.

## 4. Готовность к пилоту

Пилот начинается после принятия критичных D-02–08, готовности поддерживаемых API систем, схем и прав, настройки наблюдаемости, runbook и сроков хранения ключей. Должны пройти контрактные проверки производителей и потребителей, сценарии T-01–18, T-31–40 и отказные T-19–26 для используемых маршрутов. Пилот розницы без обязательного подтверждённого обмена магазин → WMS → закупки не принимается. SLO и бюджет нагрузки определены; по неиспользуемым расширениям явно зафиксирована граница пилота.

Проверка документального пакета подтверждает согласованность артефактов. Готовность реализации подтверждают только результаты описанных сквозных испытаний и владельцы систем.
