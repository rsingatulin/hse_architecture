# Нефункциональные требования к корпоративной информационной системе RetailMax (As-Is / To-Be)

**Статус:** Рабочий документ

---

# 1. Общая информация

## 1.1. Назначение документа

Настоящий документ содержит описание нефункциональных требований к корпоративной информационной системе предприятия RetailMax.

Документ используется в рамках проекта цифровой трансформации предприятия для определения требований к целевой архитектуре информационных систем.

Нефункциональные требования определяют ограничения и характеристики будущего решения:

- производительность;
- надежность;
- масштабируемость;
- безопасность;
- доступность;
- сопровождаемость;
- требования к данным;
- требования к интеграциям.

---

---

# 3. Текущее состояние нефункциональных характеристик (As-Is)

## 3.1. Общая характеристика

Текущая архитектура информационных систем развивалась постепенно.

Нефункциональные требования формировались преимущественно на уровне отдельных систем и не были объединены в единый корпоративный стандарт.

---

# 4. Требования к производительности

## 4.1. Текущее состояние

Основные проблемы:

- снижение скорости работы систем при росте нагрузки;
- отсутствие единого мониторинга производительности;
- сложность прогнозирования нагрузки;
- недостаточная оптимизация отдельных процессов.

---

## 4.2. Требования To-Be

| Показатель | Требование |
|-|-|
| Время ответа пользовательских операций | не более 3 секунд |
| Время ответа критичных API | не более 500 мс |
| Обработка заказа | не более 5 секунд |
| Формирование оперативных отчетов | не более 1 минуты |
| Массовая загрузка данных | выполнение в заданное окно обслуживания |

---

# 5. Требования к доступности

## 5.1. Текущее состояние

Критичные системы имеют различные уровни доступности.

Отсутствует единая политика:

- определения критичности систем;
- расчета SLA;
- резервирования компонентов.

---

## 5.2. Требования To-Be

| Система | Требование доступности |
|-|-|
| Интернет-магазин | 99,9% |
| Мобильное приложение | 99,9% |
| ERP | 99,5% |
| WMS | 99,5% |
| CRM | 99% |
| DWH | 98% |

---

# 6. Требования к надежности

## 6.1. Требования

Корпоративная система должна обеспечивать:

- отказоустойчивую работу критичных компонентов;
- сохранность данных;
- восстановление после сбоев;
- контроль состояния сервисов.

---

## 6.2. Параметры восстановления

| Параметр | Значение |
|-|-|
| RTO (Recovery Time Objective) | не более 4 часов |
| RPO (Recovery Point Objective) | не более 1 часа |

---

# 7. Требования к масштабируемости

## 7.1. Текущее состояние

Рост бизнеса приводит к необходимости:

- увеличения количества клиентов;
- роста количества заказов;
- расширения цифровых каналов.

Текущая архитектура ограничена возможностями отдельных систем.

---

## 7.2. Требования To-Be

Архитектура должна обеспечивать:

- горизонтальное масштабирование сервисов;
- добавление новых каналов продаж;
- увеличение нагрузки без существенной переработки системы.

Ожидаемые показатели:

| Показатель | Требование |
|-|-|
| Рост пользователей | до 50% без изменения архитектуры |
| Рост заказов | до 2 млн заказов в год |
| Добавление новых каналов | без изменения ядра системы |

---

# 8. Требования к безопасности

## 8.1. Текущее состояние

Основные проблемы:

- различные механизмы аутентификации;
- отсутствие единой политики доступа;
- недостаточный контроль API;
- отсутствие централизованного аудита.

---

## 8.2. Требования To-Be

Архитектура должна обеспечивать:

## Аутентификацию

Использование:

- единой системы идентификации;
- SSO;
- многофакторной аутентификации для критичных операций.

---

## Авторизацию

Использование:

- RBAC;
- управления ролями;
- принципа минимальных привилегий.

---

## Защиту данных

Требования:

- шифрование каналов передачи данных;
- защита персональных данных;
- контроль доступа к конфиденциальной информации.

---

## Аудит

Необходимо обеспечить:

- регистрацию действий пользователей;
- хранение журналов безопасности;
- анализ подозрительных операций.

---

# 9. Требования к интеграциям

## 9.1. Текущее состояние

Основные проблемы:

- точечные интеграции;
- отсутствие API Governance;
- использование файлового обмена;
- отсутствие событийной архитектуры.

---

## 9.2. Требования To-Be

Интеграционная архитектура должна обеспечивать:

| Требование | Описание |
|-|-|
| API First | новые интеграции создаются через API |
| API Gateway | централизованное управление API |
| Event Driven Architecture | обмен событиями между системами |
| Мониторинг | контроль состояния интеграций |
| Версионирование | управление изменениями API |

---

# 10. Требования к данным

## 10.1. Основные проблемы As-Is

- дублирование данных;
- различные модели данных;
- отсутствие единого владельца данных.

---

## 10.2. Требования To-Be

Необходимо обеспечить:

- единые модели данных;
- управление мастер-данными;
- контроль качества данных;
- единые идентификаторы объектов.

---

## 10.3. Критичные объекты данных

| Объект | Владелец |
|-|-|
| Клиент | CRM |
| Товар | ERP |
| Заказ | Интернет-магазин / ERP |
| Остаток | WMS |
| Финансовые данные | ERP |

---

# 11. Требования к сопровождаемости

## 11.1. Текущее состояние

Проблемы:

- недостаточная документация;
- отсутствие единого архитектурного репозитория;
- сложность анализа изменений.

---

## 11.2. Требования To-Be

Необходимо обеспечить:

- ведение архитектурной документации;
- использование Git для хранения артефактов;
- описание решений через ADR;
- автоматизацию развертывания.

---

# 12. Требования к развертыванию

## 12.1. Текущее состояние

Используется преимущественно традиционная модель развертывания приложений.

---

## 12.2. Требования To-Be

Рассмотреть использование:

- контейнеризации Docker;
- Kubernetes;
- Infrastructure as Code;
- CI/CD процессов.

---

# 13. Требования к наблюдаемости (Observability)

## 13.1. Цель

Обеспечение прозрачности работы корпоративной системы.

---

## 13.2. Требования

Необходимо контролировать:

### Метрики

- загрузку серверов;
- производительность сервисов;
- количество ошибок.

### Логи

- ошибки приложений;
- действия пользователей;
- интеграционные события.

### Трассировку

- прохождение запроса между сервисами;
- поиск причин отказов.

---

# 14. Требования к использованию искусственного интеллекта

## 14.1. Возможные направления применения AI

RetailMax рассматривает применение AI для:

- прогнозирования спроса;
- персонализации предложений;
- анализа поведения клиентов;
- автоматизации поддержки клиентов.

---

## 14.2. Требования AI Governance

Необходимо обеспечить:

- контроль качества моделей;
- защиту данных;
- прозрачность решений;
- контроль доступа к AI-сервисам.

# 17. Практическое задание

На основе документа необходимо:

1. Определить ключевые нефункциональные требования проекта.

2. Для выбранной архитектуры To-Be определить:

- какие требования являются критичными;
- какие архитектурные решения необходимы;
- какие риски возникают.

3. Подготовить:

- таблицу требований To-Be;
- архитектурные решения;
- ADR по ключевым требованиям.

Примеры ADR:

- выбор Kubernetes для развертывания;
- выбор API Gateway;
- выбор модели хранения данных;
- выбор подхода к обеспечению отказоустойчивости.
