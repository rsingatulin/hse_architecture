# 1. Общая информация

## 1.1. Назначение документа

Настоящий документ описывает текущее состояние интеграционного взаимодействия информационных систем предприятия RetailMax.

Документ является частью архитектурного репозитория проекта цифровой трансформации предприятия.

Цель документа:

- зафиксировать существующие интеграционные связи;
- определить основные потоки обмена данными;
- описать используемые способы интеграции;
- выявить ограничения текущей архитектуры;
- сформировать основу для проектирования целевой интеграционной архитектуры.

---

# 2. Общая характеристика предприятия

RetailMax — национальная торговая компания, осуществляющая продажу товаров через:

- сеть физических магазинов;
- интернет-магазин;
- мобильное приложение.

В состав предприятия входят:

- коммерческий департамент;
- отдел закупок;
- складской комплекс;
- служба маркетинга;
- финансовый департамент;
- подразделение информационных технологий.

# 4. Текущее состояние интеграционной архитектуры

Информационные системы RetailMax внедрялись независимо различными подразделениями.

Интеграция между системами создавалась по мере появления новых потребностей бизнеса.

В результате сформировалась распределенная интеграционная архитектура без единого центра управления.

---

## 4.1. Основные характеристики As-Is архитектуры

| Область | Текущее состояние |
|---|---|
| Интеграционная платформа | отсутствует |
| API Gateway | отсутствует |
| Каталог API | отсутствует |
| Управление версиями API | отсутствует |
| Мониторинг интеграций | частичный |
| Управление ошибками | ручное |
| Событийная интеграция | отсутствует |
| Единая модель данных | отсутствует |

# 7. Детальное описание интеграций

---

# INT-001. Интернет-магазин → CRM

## Назначение

Передача информации о клиентах интернет-магазина в CRM.

## Участники

Источник:

```
Интернет-магазин
```

Получатель:

```
CRM
```

---

## Передаваемые данные

| Объект данных          | Атрибуты                 |
| ---------------------- | ------------------------ |
| Клиент                 | ФИО, телефон, email      |
| Учетная запись         | дата регистрации, статус |
| История взаимодействия | действия клиента         |

---

## Способ интеграции

REST API.

---

## Текущее состояние

Интеграция используется для:

* регистрации новых клиентов;
* обновления информации о клиенте;
* маркетингового анализа.

---

## Проблемы

* отсутствует единый идентификатор клиента;
* возможны дубли записей;
* отсутствует автоматическое разрешение конфликтов данных.

---

# 9. Основные проблемы текущей архитектуры

## 9.1. Большое количество точечных интеграций

Каждая новая система требует создания отдельных связей.

Последствия:

* увеличение сложности;
* рост стоимости сопровождения;
* снижение гибкости архитектуры.

---

## 9.2. Отсутствие централизованного управления API

В компании отсутствуют:

* каталог API;
* правила проектирования API;
* управление жизненным циклом API;
* контроль версий.

---

## 9.3. Использование файлового обмена

Файловый обмен используется для критичных процессов.

Недостатки:

* задержка передачи информации;
* отсутствие оперативного контроля;
* высокая вероятность ошибок.

---

## 9.4. Отсутствие событийной интеграции

Изменения данных не передаются автоматически между системами.

Например:

* изменение остатка;
* изменение статуса заказа;
* изменение клиента.

---

## 9.5. Недостаточный мониторинг интеграций

Отсутствуют:

* единая система контроля интеграций;
* журналирование обменов;
* автоматическое оповещение об ошибках.

---

# 10. Выводы по текущему состоянию

Текущая интеграционная архитектура RetailMax обеспечивает функционирование бизнеса, однако имеет следующие ограничения:

* высокая связанность приложений;
* сложность развития цифровых сервисов;
* отсутствие единых стандартов интеграции;
* ограниченная прозрачность потоков данных.

Для дальнейшей цифровой трансформации требуется разработка целевой интеграционной архитектуры.
