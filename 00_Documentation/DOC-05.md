# Документ 5. Текущая архитектура интеграции информационных систем (As-Is)

## 1. Общая информация

Информационные системы RetailMax были внедрены в разные годы и различными поставщиками.

При внедрении новых решений интеграция выполнялась по мере необходимости, поэтому единая архитектура обмена данными отсутствует.

Большинство интеграций реализовано через REST API или обмен сообщениями через Integration Platform. При этом некоторые системы продолжают взаимодействовать напрямую.

В результате сопровождение интеграций требует значительных трудозатрат, а внесение изменений часто затрагивает сразу несколько информационных систем.

# 3. Описание интеграций

## INT-01. POS → ERP

### Назначение

Передача информации о завершенной продаже.

### Передаваемые данные

- номер продажи;
- дата;
- магазин;
- перечень товаров;
- сумма продажи;
- способ оплаты.

### Тип интеграции

REST API.

### Частота

После завершения каждой продажи.

### Выявленные проблемы

- задержки передачи данных при высокой нагрузке;
- невозможность повторной отправки при ошибке.

---

## INT-02. POS ↔ CRM

### Назначение

Получение информации о клиенте и бонусной программе.

### Передаваемые данные

- номер карты клиента;
- количество бонусов;
- персональные скидки;
- история покупок.

### Тип интеграции

REST API через Integration Platform.

### Частота

Во время оформления продажи.

### Выявленные проблемы

- увеличение времени обслуживания покупателей при недоступности CRM.

---

## INT-03. Интернет-магазин ↔ ERP

### Назначение

Получение каталога товаров и регистрация заказов.

### Передаваемые данные

Из ERP:

- товары;
- цены;
- остатки.

В ERP:

- новые заказы;
- отмены заказов.

### Тип интеграции

REST API.

### Частота

Каталог обновляется каждые 15 минут.

Заказы передаются сразу после оформления.

### Выявленные проблемы

- возможна продажа товара, который уже отсутствует на складе.

---

## INT-04. Интернет-магазин → CRM

### Назначение

Передача информации о клиентах.

### Передаваемые данные

- регистрация клиента;
- контактные данные;
- история заказов.

### Тип интеграции

REST API.

### Частота

После регистрации клиента и оформления заказа.

### Выявленные проблемы

- возможное дублирование карточек клиентов.

---

## INT-05. ERP ↔ WMS

### Назначение

Передача информации о складских операциях.

### Передаваемые данные

- поступления;
- остатки;
- задания на комплектацию;
- отгрузки.

### Тип интеграции

REST API.

### Частота

Практически в режиме реального времени.

### Выявленные проблемы

- ошибки синхронизации приводят к расхождению остатков.

---

## INT-06. ERP → BI

### Назначение

Передача данных для аналитики.

### Передаваемые данные

- продажи;
- закупки;
- финансовые показатели;
- остатки.

### Тип интеграции

ETL-процесс.

### Частота

Один раз в сутки.

### Выявленные проблемы

- аналитические отчеты строятся на устаревших данных.

---

## INT-07. CRM → BI

### Назначение

Передача информации о клиентах.

### Передаваемые данные

- клиентская база;
- бонусы;
- маркетинговые кампании.

### Тип интеграции

ETL.

### Частота

Один раз в сутки.

### Выявленные проблемы

- невозможно выполнять анализ поведения клиентов в режиме реального времени.

# 4. Использование Integration Platform

В настоящее время Integration Platform выполняет следующие функции:

- маршрутизация запросов;
- публикация REST API;
- журналирование обменов;
- преобразование форматов сообщений;
- контроль доступа к API.

Однако не все системы используют платформу интеграции.

Некоторые взаимодействия продолжают осуществляться напрямую между приложениями.

# 6. Основные проблемы текущей архитектуры

В результате анализа были выявлены следующие недостатки.

## Архитектурные

- отсутствует единая стратегия интеграции;
- имеются прямые связи между системами;
- отсутствует единый каталог API.

## Технические

- часть обменов выполняется пакетно;
- отсутствует событийная интеграция;
- отсутствует централизованный мониторинг интеграций.

## Организационные

- документация интеграций ведется частично;
- отсутствуют единые стандарты проектирования API;
- изменения интерфейсов согласуются вручную.

---

# 7. Ограничения проекта

При разработке целевой архитектуры необходимо учитывать следующие ограничения.

- ERP остается основной учетной системой.
- Полная замена информационных систем не предусматривается.
- Необходимо обеспечить совместимость с существующими приложениями.
- Простои информационных систем должны быть минимальными.
- Все новые интеграции должны использовать Integration Platform.

4. Выявить архитектурные недостатки текущей интеграции.
5. Предложить целевую архитектуру взаимодействия приложений.

7. Подготовить модель взаимодействия сервисов (C4 Container или UML Component).
